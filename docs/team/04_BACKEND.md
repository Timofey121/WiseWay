# Инструкция backend-разработчику — внешняя Demo-MVP

Дата: 9 сентября 2026 года. Исполнитель: один backend-разработчик, человек или Codex.
Результат: работающий сервер поиска и ручной сортировки полностью синтетических файлов.
План: 5 недель по 30–35 часов backend в неделю; резерв команды — ещё 1–2 недели.
Frontend работает по 30–35 часов, QA — по 15–20 часов в неделю параллельно.
Это оценка разработки, а не подтверждение готовности, допуск к коду или промышленный SLA.

## 1. С чего начать и какие документы обязательны

1. Прочитайте [вход команды](00_START_HERE.md), [ТЗ](01_PROJECT_TZ.md),
   [контракт API](02_API_CONTRACT.md) и [план исполнения](06_EXECUTION_PLAN.md).
2. Проверьте применимые `AGENTS.md`, ограничения среды и фактическую структуру репозитория.
3. Согласуйте противоречащие инструкции до продуктовой реализации; не объявляйте старые шлюзы пройденными.
4. Проверьте наличие разрешённого синтетического контекста, выбранного стека и его закреплённых версий.
5. Если решение не принято, зафиксируйте конкретный вопрос и продолжайте независимый анализ контракта.

Этот файл определяет обязанности backend, но не заменяет контракт и общее ТЗ.
Ссылки на будущие файлы задают целевые результаты, а не утверждают, что scaffold уже существует.
Не придумывайте команды запуска, имена проверочных скриптов, согласования или результаты тестов.
После создания реальных команд внесите их в README и проверьте из чистой копии проекта.

## 2. Граница продукта и ответственность

- Среда — только внешняя изолированная песочница с вымышленными компаниями и аккаунтами.
- Файлы поступают от детерминированного генератора/тестового runner, не через пользовательский upload.
- Запрещены реальные документы, названия, запросы, пути, credentials и подключения к корпоративной сети.
- Backend реализует авторизацию, доменную семантику, хранение, поиск, очередь, worker и бизнес-аудит.
- Frontend владеет пользовательским API, DTO и типизированным клиентом; backend проверяет реализуемость.
- QA владеет независимой проверкой требований и приёмочных случаев, а не утверждением за разработчика.
- Чтение метаданных и файловые изменения разделены интерфейсами и адаптерами.
- Демо доказывает поведение на синтетике, но не совместимость с внутренним хранилищем и его правами.

В демо входят несколько справочников компании, история и откат справочника, ручные batches,
no-replace move+rename, manual review, технический карантин и явный возврат из него.
В демо не входят замена занятого target, reserve, обычный файловый rollback и физическое удаление.
Не реализуйте для исключённых действий активные API, фоновые обходы или скрытые административные функции.
Возврат из карантина и откат справочника — разрешённые разные операции, не общий файловый undo.

## 3. Как работать с frontend-контрактом

Канонический файл: `contracts/openapi/memoza-demo-v1.yaml`; его владелец — frontend.
Имена routes, DTO, полей, enum, ошибок, pagination и временных полей берите из `02_API_CONTRACT.md`.
Не создавайте параллельный OpenAPI или собственные несовместимые копии публичных DTO.
Внутренние модели backend могут отличаться; преобразование в публичный контракт должно быть явным.

В первый день backend разбирает контракт, fixtures, хранение и границы адаптеров.
Frontend последовательно фиксирует первые API-срезы в дни 1–3; backend реализует принятый срез сразу.
Ждать завершения всего интерфейса запрещено: используйте согласованные schema-valid fixtures и mocks.
Для каждого среза проверьте запросы, ответы, пустые состояния, ошибки, права и конкурентные изменения.
Если поле невозможно безопасно реализовать, приложите пример и предложите конкретную коррекцию frontend.
Любое несовместимое изменение согласуется frontend + backend + QA до изменения общего поведения.
Не меняйте незаметно маршрут, обязательность поля, смысл статуса или порядок результатов.
Синхронно обновляйте схему, fixtures, backend contract tests и клиент; не оставляйте «временный» второй API.

## 4. Целевая структура backend и тестов

Структуру ниже согласуйте с общей структурой monorepo; не создавайте второй backend рядом с существующим.

```text
backend/
  app/api/                  # HTTP, session, авторизация, преобразование DTO
  app/domain/               # правила, состояния, инварианты без HTTP и физических путей
  app/services/             # сценарии поиска, публикации, очереди и запуска
  app/ports/                # интерфейсы metadata, storage mutation, index, persistence, audit
  app/adapters/             # синтетическая песочница и адаптеры выбранного стека
  migrations/               # версионированные изменения служебной БД
  tests/unit/               # parser, matcher, состояния, проверки и преобразования
  tests/contract/           # соответствие каноническому OpenAPI и общим fixtures
  tests/integration/        # БД, индекс, файловая песочница, restart и concurrency
tests/e2e/                  # общие сквозные случаи, согласованные с frontend и QA
```

Физический root хранится только в серверной конфигурации; браузеру доступны логические идентификаторы.
Целевые и служебные директории заранее создаёт контролируемая подготовка песочницы, не сортировщик.
Все операционные корни демо находятся на одной файловой системе; cross-filesystem fallback отсутствует.

## 5. BE-01 — основание сервиса, сессии, конфигурация, аудит

Цель: получить проверяемый серверный каркас и персональную атрибуцию каждой операции.
Зависимости: согласованная структура/стек; первый принятый контрактный срез для публичных API.
Файлы: `backend/app/api`, `backend/app/adapters`, `backend/migrations`, `backend/tests`.
Действия:

- Создайте приложение, конфигурацию профиля, миграции и воспроизводимый старт выбранного стека.
- Добавьте локальный вход и сессии по контракту; используйте только вымышленные тестовые аккаунты.
- Разделите рабочую и административную роли; проверяйте права на сервере при каждом действии.
- Не делайте выбор компании ACL: рабочие пользователи имеют одинаковые прикладные права.
- Храните пароли безопасным salted hash; не встраивайте secrets в код, fixtures и документацию.
- Реализуйте append-only аудит с серверным временем, actor, correlation и связями предметных операций.
- Отделите бизнес-журнал от системных/auth-событий; не пишите запросы поиска и request bodies в логи.

Зачем: поиск и worker должны использовать единые права, конфигурацию и доказуемую историю.
Проверка: миграции на пустой БД, вход/выход, отказ без сессии/прав, доступность только разрешённого аудита.
Ожидаемый результат: frontend подключает настоящий session API; журнал сохраняется после перезапуска.

## 6. BE-02 — метаданные, parser, индекс и поиск

Цель: вернуть точные результаты, маркеры и счётчики из одного согласованного набора данных.
Зависимости: BE-01; принятый контракт поиска и синтетическая схема уровней из общего ТЗ.
Файлы: `backend/app/domain`, `backend/app/services`, `backend/app/ports`, `backend/app/adapters`.
Действия:

- Реализуйте metadata-only обход разрешённых regular files без чтения содержимого и выхода за root.
- Исключите служебные incoming/manual_review/quarantine и технические файлы по demo-конфигурации.
- Реализуйте parser уровней и остановку на первой структурной ошибке; не угадывайте значения.
- Добавьте «Не распознано», точные counts и единое AND-пересечение текста с выбранными маркерами.
- Реализуйте whole-token quoted phrase и согласованный prefix-поиск без fuzzy и исправления опечаток.
- Используйте стабильную серверную сортировку и tie-breakers из общего ТЗ, без пересортировки клиентом.
- Отдавайте только текущие имена/пути; старые реквизиты выполненных операций храните отдельно в аудите.
- Поддержите изменение/исчезновение файлов и обновление read model после успешной операции worker.
- Показывайте точное total и ограниченную выдачу по контракту; не скрывайте ошибку пустым успехом.

Зачем: интерфейс должен видеть совпадающие таблицу, total и варианты следующего уровня.
Проверка: golden fixtures для обычных/ошибочных путей, кавычек, prefix, нуля, лимита, ties и обновлений.
Ожидаемый результат: реальные search API проходят contract tests и дают утверждённые exact results.

## 7. BE-03 — справочники, версии, simulation и публикация

Цель: детерминированно применять полный набор опубликованных справочников выбранной компании.
Зависимости: BE-01; контракт справочников; simulation подключается к READY-набору BE-04.
Файлы: `backend/app/domain`, `backend/app/services`, `backend/migrations`, `backend/tests/unit`.
Действия:

- Поддержите несколько справочников компании: stable ID, уникальное название, необязательное описание.
- Добавьте один общий draft на справочник, revision-проверки, неизменяемые версии и одну active version.
- Отклоняйте устаревшую правку целиком, без auto-merge, частичной записи и тихой перезаписи.
- Реализуйте обязательный match field, whole-string glob, priority 1–1000 и fixed target stem.
- Соблюдайте правила case-folding, разделителей и расширения из ТЗ; не добавляйте regex и шаблоны имени.
- Объединяйте все active versions компании на сервере; selector справочника в запуске запрещён.
- Сравнивайте все совпадения минимального priority; разные target tuples дают конфликт правил.
- Для одинакового итогового tuple используйте стабильную attribution, согласованную в контракте/ТЗ.
- Тестируйте кандидат как замену одной версии в полном наборе на всех READY items, независимо от UI-фильтра.
- Блокируйте publish при любом конфликте; для ненулевого «Нет сценария» требуйте exact-snapshot acknowledgment.
- Инвалидируйте simulation при изменении draft, входящих версий набора, READY-состава или истечении срока; проверяйте target directories.
- Откат проходит restore-draft → simulate → publish. Публикация меняет одну active version, требует комментарий и оставляет неизменяемую историю.

Зачем: два пользователя и несколько справочников не должны приводить к скрытому изменению плана файла.
Проверка: границы glob/extension, разные/одинаковые tuples, revision conflict, stale simulation и rollback.
Ожидаемый результат: версии воспроизводимы; новый набор действует для новых запусков, не для принятых batches.

## 8. BE-04 — readiness, очередь, snapshots и preview

Выполняйте двумя подэтапами: BE-04a — обнаружение, готовность и чтение очереди сразу после BE-01;
BE-04b — снимки/preview после matcher BE-03. Simulation BE-03 использует READY-набор BE-04a.
Так BE-03 и BE-04 не блокируют друг друга циклической зависимостью.

Цель: закрепить точный состав ручного запуска и исключить обработку незавершённого/изменившегося файла.
Зависимости: BE-01; контракт очереди; matcher BE-03 подключается через согласованный внутренний интерфейс.
Файлы: `backend/app/services`, `backend/app/domain`, `backend/migrations`, `backend/tests/integration`.
Действия:

- Обнаруживайте файлы внутри incoming; изменение/rename инвалидирует старые сведения, delete даёт MISSING.
- Demo-readiness: два одинаковых наблюдения metadata/fingerprint с интервалом не менее 5 секунд.
- Это настройка внешней песочницы, не доказательство готовности файла на внутреннем хранилище.
- До выбора компании не отдавайте общую очередь; рассчитывайте три counters и единый фильтр статусов.
- Создавайте immutable snapshot точных IDs/revisions по выбору или нормализованным текущим фильтрам.
- Возвращайте точное количество; поздние поступления и страницы браузера не меняют сохранённый состав.
- Рассчитывайте необязательный preview по полному текущему набору и проверенным целям без FS mutation.
- Не подменяйте stale items новыми совпадениями; требуйте явного обновления snapshot/preview по контракту.
- Проверяйте занятые цели и одинаковые итоговые targets выбранных items до физических изменений.

Зачем: «Все подходящие» должно означать сохранённый серверный набор, а не текущую страницу таблицы.
Проверка: позднее поступление, rename, delete, изменения правил, истёкший preview и независимость от пагинации.
Ожидаемый результат: frontend показывает точный состав, причины и актуальность; просмотр не запускает worker.

## 9. BE-05 — безопасный executor, batches и возврат из карантина

Цель: выполнить максимум безопасных items один раз и сохранить точный результат каждого.
Зависимости: BE-01, BE-03, BE-04; принятый run/batch/quarantine контракт; проверенный sandbox adapter.
Файлы: `backend/app/services`, `backend/app/ports`, `backend/app/adapters`, `backend/tests/integration`.
Действия:

- При ручном submit повторите preflight, атомарно claim-ите items и закрепите source/rule-set/plan.
- Занятый другим batch item получает «Уже обрабатывается»; остальные безопасные items продолжаются.
- Выполняйте atomic no-replace move+rename; проверяйте containment, source identity и цель перед мутацией.
- При неподдерживаемой гарантии/другой файловой системе отказывайте; copy+delete не является fallback.
- TARGET_OCCUPIED оставляет source во incoming как REQUIRES_DECISION, без замены и reserve.
- NO_SCENARIO/RULE_CONFLICT после запуска физически направляйте в плоский manual_review компании.
- Сохраняйте проверенный фактический исходный basename; не создавайте подпапки, suffix и новые имена.
- Занятость manual-review basename оставляет source во incoming, без overwrite/quarantine и auto-retry.
- Направляйте в technical quarantine только известный технический отказ с доказанным расположением source.
- Не маскируйте неоднозначный FS outcome карантином: остановите повтор и передайте случай на ручной разбор.
- Сохраняйте durable intent/phase/result; после restart сначала доказывайте состояние, а не повторяйте move.
- Для return проверьте права, обратимость, identities и свободный original incoming path до любой мутации.
- Return требует подтверждение и комментарий; после успеха ставьте WAITING_READY, очищайте старый план.
- Не создавайте sorting job после return; повторный запуск — только вручную после новой readiness-проверки.

Зачем: HTTP retry, гонка операторов и сбой процесса не должны породить второе файловое действие.
Проверка: no-replace, обе коллизии, idempotency, overlap, stale source, известный отказ и ambiguous outcome.
Ожидаемый результат: durable batch totals/per-item outcomes и неизменяемый audit совпадают с файлами.

## 10. BE-06 — интеграция, сборка и проверки перезапуска

Цель: передать команде воспроизводимую работающую демо, а не набор успешных mock-ответов.
Зависимости: вертикальные срезы BE-01…BE-05; frontend интеграция начинается до завершения всех срезов.
Файлы: backend integration tests, `tests/e2e`, реальные README/команды сборки и конфигурация запуска.
Действия: подключите UI к настоящим API, устраните contract drift, проверьте миграции и restart/recovery.
Зачем: серверные компоненты должны работать вместе из чистой копии на одинаковых synthetic fixtures.
Проверка: unit + contract + integration + согласованные E2E, отсутствие secrets/реальных данных в артефактах.
Ожидаемый результат: сборка воспроизводима; известные ограничения записаны; обязательные проверки проходят.

## 11. Порядок работы, передача и приёмка

Неделя 1: обзор контракта с первого дня, BE-01 и начало BE-02; первые реальные API после фиксации срезов.
Неделя 2: BE-02 и ядро BE-03; совместная проверка search и справочников с frontend/QA.
Неделя 3: BE-03, BE-04 и ранние безопасные executor cases; не откладывайте storage-risk tests на финал.
Неделя 4: BE-05, интеграция очереди/истории/карантина, concurrency и interruption tests.
Неделя 5: BE-06, исправления, независимая QA-приёмка и подготовка чистого пакета запуска.
Резерв 1–2 недели расходуется на найденные риски; расширение scope требует отдельного согласования команды.

Каждый handoff содержит точный commit/ref, принятый срез контракта, изменённые миграции и реальные команды.
Приложите проверенные fixtures, результаты тестов, ограничения, известные дефекты и следующий доступный срез.
Разделяйте «реализовано», «локально проверено» и «принято QA»; не объявляйте принятие от имени QA.
Приёмка требует совпадения API со схемой, exact search results, no-replace invariants и полного per-item audit.
Не допускаются слепой повтор после ambiguous outcome, потеря истории, обход root и неподдерживаемая замена.
Следующее действие: вместе с frontend проверьте первый контрактный срез и зафиксируйте замечания backend/QA.
