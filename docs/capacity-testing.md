# Проверка 200–400 млн записей

Это нагрузочный стенд для **синтетических метаданных**, а не файловый архив.
Он использует обычные `ArchiveImporter`, OpenSearch и авторизованный API.
Полезная нагрузка файлов, SMB, внешняя аутентификация и резервное восстановление
200 ТБ этим тестом не проверяются. До завершения прогона целевой объём не считается подтверждённым.

## Данные и ограничения

Корпус `diverse`: 64 компании, 128 проектов, 8 категорий, 32 семейства имён,
уникальные ID/пути, разные размеры и даты. Распределение детерминированное;
семейства имён и компании коррелируют. Оно разнообразнее старого `baseline`
из двух компаний, но не заменяет выборку реального архива. Высокую кардинальность
фасетов, длинные пути и редкие Unicode-случаи дополнительно проверяют отдельные тесты.

Генератор пишет не более одного миллиона записей в очередной immutable manifest.
Первый блок импортируется как полный снимок, следующие — как дельты в тот же
физический индекс. После подтверждения публикации сохраняется checkpoint и
удаляется только подтверждённый исходный блок. При остановке повторяется тот же
незавершённый блок и базовое поколение. Такой прогон проверяет **накопление**
большого индекса, а не один полный импорт 400-миллионного manifest.

Каталог защищён marker-файлом и блокировкой. Corpus, shards, batch size и размер
блока должны оставаться прежними при возобновлении; целевой `--records` можно
увеличивать до 400 млн. Чужие существующие каталоги не принимаются.

## Локальный Linux-стенд в Docker

```sh
docker compose -f infra/opensearch/compose.capacity.yaml --profile benchmark build benchmark
docker compose -f infra/opensearch/compose.capacity.yaml up -d --wait search

# Сначала короткая проверка CLI, импорта и API.
docker compose -f infra/opensearch/compose.capacity.yaml run --rm benchmark \
  --data-dir /benchmark/pilot --corpus diverse --shards 4 --batch-size 5000 \
  --records 10000 --phase all --clients 4 --repeats 3
```

Стенд ограничивает OpenSearch четырьмя CPU и 5 GiB RAM, JVM heap — 2 GiB;
контейнер API/импортера — двумя CPU и 2 GiB RAM. Кеш ответов API отключён.
Порт движка опубликован только на `127.0.0.1:19400`. Отключённая аутентификация
движка допустима исключительно для этого синтетического стенда.

Для длительного прогона запускайте и защиту **физического диска хоста**:

```sh
docker compose -f infra/opensearch/compose.capacity.yaml run -d \
  --name wiseway-capacity-run benchmark

python3 infra/scripts/capacity_watch.py \
  --client wiseway-capacity-run --search wiseway-capacity-search-1 \
  --path /private/tmp --min-free-gib 40
```

На Linux замените `--path` на каталог файловой системы, содержащей Docker data
root. На macOS это должна быть файловая система, содержащая диск Docker Desktop.
Импортер также проверяет резерв внутри контейнеров (по умолчанию 20 GiB).
Оба резерва нужны: свободное место виртуального диска не равно месту на хосте.
Watcher проверяет метку контейнеров, обращается к их неизменяемым ID и при
недостатке места останавливает импортер и движок, включая фоновые merge.
Он также останавливает движок после завершения клиента; тома сохраняются.

```sh
docker logs --tail 20 wiseway-capacity-run
docker compose -f infra/opensearch/compose.capacity.yaml run --rm benchmark \
  --data-dir /benchmark/archive --phase status
```

После прерывания поднимите `search` и повторите запуск с новым именем контейнера,
тем же `/benchmark/archive` и теми же параметрами. Для перехода от 200 к 400 млн:

```sh
docker compose -f infra/opensearch/compose.capacity.yaml up -d --wait search
docker compose -f infra/opensearch/compose.capacity.yaml run -d \
  --name wiseway-capacity-run-400 benchmark \
  --data-dir /benchmark/archive --corpus diverse --shards 4 --batch-size 5000 \
  --records 400000000 --phase all
```

Сразу запустите watcher для нового имени контейнера. Команда не гарантирует,
что места хватит до цели: резерв останавливает тест, а не увеличивает ёмкость.
Старые полные физические индексы приложение автоматически не удаляет.
Для полного rebuild нужно место одновременно под старый и новый индекс,
транзакционный журнал, merge и эксплуатационный резерв.

## Как читать результат

`completed_records` — подтверждённое накопленное число записей; `pending_chunk`
обозначает незавершённый блок. `capacity-result.json` содержит результаты API,
ошибки и отдельную проверку SLA: p95 типичных запросов ≤2 с, широких ≤5 с.
Ненулевой код выхода нельзя считать успешным испытанием. При возобновлении
время текущего процесса не является временем всей первоначальной загрузки.

Нагрузка проходит через ASGI: один аккаунт/сессия, до 50 конкурентных клиентов,
без клиентского TCP/TLS и без сброса кешей ОС/OpenSearch. Это не проверка 50
одновременных логинов. Для числового SLA реального продукта нужны целевые
CPU/RAM/NVMe, реальные распределения запросов и данных, а также чтения на фоне
потока изменений. Лимит v1 в 10 000 вариантов одного фасета остаётся: для большего
числа вариантов требуется согласовать пагинацию с frontend.
