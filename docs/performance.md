# Производительность и рост архива

## Исходные границы

ТЗ оценивает будущий архив примерно в **195 ТБ логически** и **93 ТБ физически после сжатия 2,1**. Это исходная оценка, не обследование. Поиск читает только метаданные, имя и путь: размер содержимого файла не определяет размер индекса. Если средний файл близок к 1 MB, 200 ТБ означает около **200 млн файлов** в десятичных единицах; при среднем размере 0,5–2 MB диапазон составляет примерно 100–400 млн файлов.

Для текущей эксплуатации задан один Linux-сервер и до 50 пользователей. Для целевого сервера пока не заданы CPU, RAM, класс SSD, фактическое число файлов и папок, кардинальности уровней, скорость обхода и канал изменений. ТЗ уже задаёт цель: потеря служебных данных не более часа (RPO ≤1 часа), восстановление служебных компонентов не более четырёх рабочих часов (RTO ≤4 рабочих часов). Неизвестно, можно ли достичь этих целей на будущем объёме: это требуется доказать резервным копированием и восстановлением. Поэтому числовой SLA на архиве объявлять рано. В ТЗ для согласованного стенда ориентиры p95: типичный поиск не более 2 секунд, широкий — не более 5 секунд.

## OpenSearch и потоковый импорт

Добавлен отдельный поисковый движок с компактными документами, фиксированным
контрактным ранжированием, точными фасетами и публикацией через PIT. Импортер
читает неизменяемые manifests порциями, возобновляет работу с byte offset и
применяет только дельты. Основная SQLite больше не хранит строки этого архива.
Кеш повторов ограничен 8 MiB и привязан к снимку; его можно отключить для замеров.
[Инструкция, модель сбоев и эксплуатационные ограничения](archive-search.md).

Ни наличие OpenSearch, ни замер миллиона сами по себе не подтверждают SLA на
200–400 млн записей. Требуются реальные распределения путей, кардинальности
фасетов, поток изменений и параметры Linux-сервера.

## Проверка OpenSearch на 10 млн записей

Linux ARM64 в Docker на Apple M3 (8 CPU, 16 GiB). OpenSearch 3.8.0: **2 CPU,
3 GiB, heap 768 MiB, 2 primary shards, без replicas**. Импортер/API:
отдельный контейнер **2 CPU, 3 GiB**. Суммарный лимит больше, чем у прежнего
SQLite-теста: прямое сравнение затрат железа между движками некорректно.

10 млн синтетических записей загружены за **1189,856 с** (около 8404/с).
Peak RSS импортера — **115,4 MiB**. Primary store после refresh —
**1 593 995 888 байт**; это не backup, не общий размер тома и не окончание всех
фоновых merge. Payload-файлы не создавались и не читались. Корпус содержит две
компании, два проекта и сильно повторяющиеся пути: его компрессия не является
прогнозом для реального архива.

Последовательные запросы через авторизованный ASGI API, первый вызов + 5
повторов; **кеш ответов API отключён**. Кеши ОС/OpenSearch обычные, не сбрасывались.
«Первый» означает первый запрос нового процесса, а не холодный диск.

| Сценарий | Первый, мс | p50 повторов, мс | p95 повторов, мс |
|---|---:|---:|---:|
| Одно совпадение | 12,565 | 5,302 | 7,252 |
| Нет совпадений | 4,231 | 3,324 | 3,852 |
| Все 10 млн | 60,837 | 19,543 | 20,722 |
| AND, 5 млн | 46,984 | 29,550 | 105,131 |
| Фраза, 5 млн | 21,823 | 20,491 | 79,115 |
| Маркеры + текст, 5 млн | 16,592 | 16,144 | 24,810 |

Смешанный burst: 50 клиентов, один аккаунт/сессия, 250 запросов
(120 редких, 125 пустых, 5 широких). p95 с очередью: **182,793 / 186,266 /
212,883 мс**, ошибок 0, peak RSS API **126,94 MiB**. В отдельном burst из
**50 широких запросов** p95 составил **724,201 мс**, ошибок 0. Это ASGI,
без TCP/TLS клиента, логинов и параллельной индексации; нагрузка 50 разных
аккаунтов и произвольных уникальных запросов сюда не входит.

Оптимизация проверена на том же 10-миллионном индексе: до разделения счётчиков
и ранжирования широкие запросы имели p95 **699,854 мс**, а burst из 50 широких —
**35 906,285 мс**. После — **20,722** и **724,201 мс** соответственно. Счётчики
определяются по токенам пути; filename и маркеры являются его частями.
Максимально возможная оценка каждого слова/фразы проверяется отдельными
фильтрами. Если пересечение максимальных оценок заполняет top-k, достаточно
сортировки по пути; иначе выполняется полный точный scorer. Golden-тесты
проверяют оба варианта, включая несовместимые максимумы разных слов.

Кеш API дополнительно объединяет одинаковые конкурентные вычисления и хранит
ответы до 30 секунд в пределах 8 MiB. Приведённые окончательные цифры не зависят
от этого кеша. Медленные поиски имеют отдельные 4 слота и не занимают 4 слота
сессий, аудита и бизнес-операций.

При 200–400 млн точные счётчики и резервный scorer могут стать дорогими;
память для рабочего набора, NVMe, число шардов и распределение запросов
определят реальный результат. Линейное умножение времени или размера этого
синтетического корпуса не подтверждает SLA. Новый профиль существенно
ускоряет проверенную нагрузку, но **200–400 млн ещё не испытаны**.

После настоящего перезапуска OpenSearch на этом корпусе проверены ожидаемый
503 при потере PIT и восстановление точной выдачи 10 000 000 / 100 через
`maintain-search`, без повторного импорта. Это проверка рестарта процесса,
а не восстановления утраченного диска или полного архива из backup.

## Подготовка более крупного испытания

Добавлен [возобновляемый capacity-стенд](capacity-testing.md): загрузка
ограниченных порций, независимая проверка количества/выдачи/фасетов, отдельный
отчёт SLA и резерв свободного места внутри Docker и на хосте.

Новый пилот содержит **1 000 000 разнообразных записей**: 64 компании,
128 проектов, 8 категорий, 32 семейства имён, разные даты и размеры.
Linux ARM64 на том же Mac; OpenSearch ограничен 4 CPU / 5 GiB (heap 2 GiB,
4 primary shards), клиент — 2 CPU / 2 GiB. Построение с генерацией исходного
manifest заняло **112,656 с**, peak RSS клиента — **117,63 MiB**. Primary store
после перезапуска движка — **502 241 336 байт**, live documents — ровно миллион.
Это пилот с сортировкой физического индекса, до отключения inverted index у
служебных полей и до оптимизации bulk-сериализации.

Через авторизованный ASGI API без кеша ответов проверены редкие, отсутствующие,
широкие запросы, фильтрация компанией и сортировки. Из 250 запросов при 50
конкурентных клиентах половина широкие: p95 типичных — **641,757 мс**, широких —
**674,503 мс**, ошибок нет. Кеши ОС/движка не сбрасывались; TCP/TLS и одновременные
логины не включены. Для PATH DESC, MODIFIED_AT DESC и SIZE DESC большой пилот
проверяет total; точный порядок проверен отдельными малыми golden-тестами.

Размер нового корпуса существенно выше старого двухкомпанейного. Нельзя
переносить его сильное сжатие на реальный архив. Простое умножение 502 байт
на 400 млн даёт около 201 GB только primary store; журнал, merge, резервная
копия и старое поколение при rebuild требуют дополнительного места.

В изолированном сравнении на 100 тыс. разнообразных записей (2 primary shards)
комбинация сортировки физического индекса по пути и отключения doc values для
двух полей фильтрации дала: загрузка 12,605 → 14,041 с, primary store
61 275 664 → 57 655 301 байт, тёплый широкий запрос p50 16,492 → 7,717 мс,
p95 67,227 → 24,020 мс. Проверены точные результаты и versioned tombstones.
Это совместный эффект двух настроек на малом синтетическом корпусе; отдельно
приписывать выигрыш одной настройке или переносить SLA на 400 млн нельзя.

Следующее отдельное сравнение 100 тыс. записей при одинаковой сортировке
индекса отключило inverted index у полей, используемых только для сортировок
и агрегаций. Primary store: **48 619 357 → 39 852 573 байт (−18,0%)**;
загрузка: **16,474 → 13,382 с**. Все сортировки, total, фасеты, фильтры маркеров
и versioned tombstones совпали. Варианты запускались последовательно, поэтому
разницу latency нельзя отделить от прогрева и merge; утверждения об улучшении
SLA по этому A/B нет. Статические настройки применяются при новом полном импорте.
Размеры повторно подтверждены с отключённым кешем store statistics только у
временных A/B-индексов: **48 619 357 → 39 852 573 байт**. Обычная статистика
движка обновляется с задержкой и сразу после публикации может занижать размер.

Сравнение bulk на 100 тыс. записей, по два прогона в прямом и обратном порядке,
одинаковый mapping и предел 5 000 записей: среднее время прежнего импортера —
**10,712 с**, однократная сериализация с целью 4 MiB — **9,957 с**, с целью
12 MiB — **9,586 с**. Количество запросов — **67 / 43 / 20**, в каждом случае
передано ровно **180 193 788 байт**, PIT содержит ровно 100 тыс. живых документов.
Это около **10,5%** выигрыша конечного варианта в этом небольшом сравнении.
Peak RSS общего процесса всех шести прогонов — **145,43 MiB**; это общий максимум,
а не независимое измерение памяти каждого варианта. fsync и порядок checkpoint
сохранены. Предзагрузка следующей пачки потоками пока не включена: после этих
изменений CPU подготовки документов занимает большую часть времени.

Подготовка полных документов индекса в Python для 20 тыс. валидных записей
разнообразного корпуса: исходный `707fc55` — 0,9921 с, подготовленная один раз
схема — 0,6646 с. Этот замер исключает сетевой bulk, fsync и работу движка.

## Возобновлённый прогон на 25 млн записей

Тот же разнообразный корпус и стенд 4 CPU / 5 GiB, heap 2 GiB, 4 primary
shards были возобновлены с подтверждённой точки 13 млн до **25 000 000**.
Двенадцать новых блоков импортированы за **1231,324 с** (около 9746 записей/с);
peak RSS клиента — **102,63 MiB**. Каждый блок публиковался отдельно, после
завершения `pending_chunk` равен null. Никаких файловых payload стенд не создавал.
Этот накопленный индекс имеет формат `wiseway-search-2`, существовавший до
добавления отдельного ключа сортировки дробных UTC-дат.

После остановки и настоящего перезапуска OpenSearch индекс содержит ровно
25 млн live documents, 0 deleted documents и 51 segment. Primary store —
**4 697 681 689 байт**, translog — 220 байт и 0 операций. Это около 188 байт
primary store на запись для данного корпуса после restart; ранние снимки размера
во время импорта были выше из-за translog и незавершённых merge.

Авторизованная ASGI-проверка без кеша приложения подтвердила total, первые ID,
фасеты и заявленные сортировки. Последовательный широкий запрос имел p95
**156,200 мс**. В burst из 250 запросов с 50 клиентами p95 типичных запросов —
**1155,583 мс**, широких — **1203,671 мс**; ошибок нет, цели 2/5 секунд пройдены.
Лучший результат относительно более ранней точки 10 млн нельзя считать
ускорением от роста индекса: кеши не сбрасывались, а короткий burst имеет
вариативность.

Отдельный полный пилот текущего mapping `wiseway-search-3` на 1 млн записей
после restart занял **387 471 734 байта** против **384 186 607 байт** у v2
пилота в том же томе: поле `modified_key` добавило около 0,86% primary store.
Mapping и наличие поля подтверждены через OpenSearch API; корректность и SLA
v3 прошли, burst p95 — 612,376/631,828 мс. Его загрузка заняла 244,520 с,
но это не чистое сравнение throughput: движок одновременно сохранял большой
v2 индекс и несколько интеграционных индексов.

Линейная оценка одного primary поколения по стабильному размеру 25-миллионного
v2 индекса даёт около 37,6 GB для 200 млн и 75,2 GB для 400 млн; измеренная
надбавка v3 мала, но не доказывает постоянный коэффициент на большом объёме.
Это оценка ёмкости, а не завершённый
тест или гарантия задержки. Полный rebuild одновременно держит старое и новое
поколения и требует дополнительного места под merge, snapshots и резерв.
Текущий Docker-диск 180 GiB не даёт безопасного эксплуатационного запаса для
такого rebuild на 400 млн. Фактически подтверждены 25 млн; 200–400 млн и
целевой Linux-сервер ещё не подтверждены.

## SQLite-режим и предыдущие оптимизации

Старый опубликованный индекс хранился одним JSON-документом и загружался целиком. Для больших корней добавлен постоянный SQLite-режим поиска:

- метаданные файлов и маркеры хранятся отдельными строками поколения; полнотекстовый индекс использует тот же поток токенов, что и контрактный поиск;
- новое поколение создаётся в состоянии `BUILDING`, наполняется ограниченными транзакциями, затем становится `READY` и атомарно публикуется как `ACTIVE`;
- опубликованный объект корня содержит ссылку на поколение, а не массив всех файлов; читатель завершённого поколения не переключается на незавершённое;
- API сохраняет правила контракта: один корень, AND и prefix для токенов, фразы, цепочку маркеров, фасеты с точными счётчиками, естественный порядок и ограничение первых N результатов;
- обычный индексатор сохраняет checkpoint порциями и не переписывает весь накопленный префикс; локальная файловая блокировка не допускает двух экземпляров одного индексатора.

Журнал аудита читает страницы через SQLite keyset-курсор с границей видимого набора. Списки партий и очередь выбирают связанные строки индексированными запросами. Эти изменения уменьшают полные чтения JSON и удерживаемую память в обычных операциях.

`LargeIndexer` — отдельный ограниченный staging-обход, пока не выбран регулярным worker. Его progress/checkpoint показывает состояние работающего запуска, но не является crash-resume: после stop/crash незавершённый обход отбрасывается и начинается заново, а любое замеченное изменение приводит к полному перестроению поколения. Пределы одного обхода: 1 100 000 записей, глубина 64, суммарно 512 MiB путей и 3 600 секунд на префикс. Они специально не позволяют выдать текущую реализацию за обход 200 млн файлов.

Миграции индексов требуют полной резервной копии и окна обслуживания: на большой БД их создание может быть долгим. SQLite в WAL-режиме имеет одну запись одновременно; это описано в [официальной документации SQLite](https://www.sqlite.org/wal.html). SQLite остаётся подходящим для текущего одиночного сервера и ограниченного числа пользователей, но это не утверждение о готовности к 200 млн файлов.

## Сохранённые локальные измерения

Сравнение с `60154d3`: macOS ARM64, Python 3.11.5, одинаковые синтетические корпуса. Это полезная регрессия кода, не характеристика будущего Linux-сервера.

| Сценарий | До | После |
|---|---:|---:|
| API/SQLite, 10 000 записей, редкое совпадение | 176,81 мс | 2,86 мс |
| API/SQLite, 10 000 записей, широкий поиск | 235,87 мс | 11,77 мс |
| Подготовленный алгоритм, 100 000 записей, широкий поиск | 362,80 мс | 152,52 мс |
| Перестроение индекса 9 505 файлов | 5,774 с | 0,469 с |
| Список 200 партий / 10 000 попыток | 3 164,35 мс | 27,76 мс |
| Проверка новых событий из журнала 50 000 записей | 186,40 мс | 0,44 мс |

API-стенд включает ASGI, SQLite и валидацию ответа, но не реальный TCP и не обход файловой системы. Стенд алгоритма на 100 000 записей намеренно обходил прежний предел prepared-индекса; он не доказывает готовность всей системы на 100 000 файлов. Нагрузка 50 аккаунтов и 12 500 TCP-запросов завершилась без 5xx и SQLite busy, но короткий прогон не подтверждает SLA или длительную устойчивость целевого сервера.

## Миллион записей

Завершённый корпус: **1 000 000 строк**, опубликованное поколение `ACTIVE`, БД 3 791 532 032 байта (3,53 GiB). Apple M3 (8 ядер), 16 GiB RAM хоста; Linux ARM64 в Docker Desktop, Python 3.11.15, квота контейнера 2 CPU, лимит контейнера 3 GiB, `/tmp` 512 MiB, данные в локальном Linux volume. Исходный prepared-поиск `23016b1` был остановлен OOM-killer при лимите 3 GiB; это отказ старого алгоритма по памяти, а не парное сравнение задержки успешных ответов.

Итоговый последовательный прогон на том же корпусе: один первый запрос и пять повторов каждого вида. Проверены точные ID, порядок, total и фасеты. При пяти повторах столбец p95 фактически равен максимуму выборки; он не подтверждает эксплуатационный SLA.

| Запрос | Первый, мс | Медиана повторов, мс | p95 повторов, мс |
|---|---:|---:|---:|
| Редкое совпадение (1 файл) | 130.7 | 49.5 | 53.7 |
| Нет совпадений | 12.3 | 10.1 | 10.8 |
| Широкий поиск (1 млн файлов) | 3815.9 | 3226.3 | 5220.8 |
| AND (500 тыс. файлов) | 4416.8 | 3152.2 | 5707.6 |
| Фраза (500 тыс. файлов) | 1720.9 | 2349.5 | 2521.4 |
| Текст и маркеры (500 тыс. файлов) | 3966.5 | 2896.5 | 4766.1 |

**Параллельная нагрузка:** 50 клиентов, 250 ASGI-запросов, одна заранее созданная сессия одного синтетического аккаунта. Состав: 120 редких, 125 пустых и 5 широких запросов. Все ответы корректны, ошибок нет. p95 с ожиданием в очереди: редкие 6 105 мс, пустые 5 916 мс, широкие 14 503 мс; пик RSS процесса 128,34 MiB. Это короткий селективный burst без TCP, 50 разных аккаунтов, одновременной индексации или проверки login. **Цели задержки 2/5 секунд на таком burst не выполнены.** Даже последовательные широкие запросы иногда превышали 5 секунд.

Устранены повторное вычисление кандидатов, лишние exact/prefix совпадения и декодирование всего корпуса. TEMP хранит только ID и оценку; JSON читается для ограниченной страницы. SQL-запрос имеет бюджет 30 секунд, после которого возвращается retryable `SEARCH_UNAVAILABLE` (503). Бюджет не включает ожидание свободного обработчика и не является SLA.

Отдельно выполнены полные обходы настоящих файлов с разбором метаданных и публикацией индекса:

| Файлы | Время обхода и построения | Peak RSS |
|---|---:|---:|
| 100 000 пустых + 5 seed-файлов | 15,345 с | 85,28 MiB |
| 1 000 000 пустых + 5 seed-файлов | 321,986 с | 187,80 MiB |

Создание и удаление тестовых файлов в это время не включены. Это локальная файловая система, не SMB и не чтение содержимого файлов. На миллионе полный цикл уже превышает пять минут, поэтому режим полного перестроения не подтверждает требуемую свежесть при изменениях. Рост времени оказался существенно больше десятикратного — линейно переносить малый замер на большой архив нельзя.

Сценарий `backend/benchmarks/million.py` создаёт только синтетические метаданные, а не терабайты файлов. Он строит постоянное SQLite-поколение пакетами по 1 000 строк, заново открывает приложение отдельным процессом и проверяет первые и повторные запросы: редкое и отсутствующее совпадения, широкий AND/phrase поиск, цепочку маркеров, IDLE, фасеты, первые 100 ID и публичный ответ списка корней. Он выводит время сборки, размер DB/WAL и peak RSS. Первый запрос после старта процесса не означает сброс page cache ОС. Корпус имеет только две компании и несколько общих веток: большие кардинальности фасетов, разнообразие реальных путей и распределение запросов требуют отдельного стенда. Измерение не включает реальный TCP и файловый обход.

## Чего текущая реализация не доказывает

- Нет проверки на 100–400 млн записей; подтверждённые 25 млн не доказывают линейную задержку при дальнейшем росте.
- Нет проверки на целевом Linux-сервере с известными CPU, RAM, SSD и файловой системой.
- Масштабирование архивного поиска не расширяет лимиты входящей очереди. Большие очереди, история партий и операторский status всё ещё требуют отдельной проверки и замены оставшихся полных выборок.
- Нет промышленного источника изменений от SMB/CIFS/NFS или другого корпоративного хранилища; текущий обход и его пределы нельзя переносить на реальный архив без адаптера и испытаний.
- Цели RPO ≤1 часа и RTO ≤4 рабочих часов уже заданы ТЗ, но не подтверждены восстановлением большого индекса; также неизвестны место под резервы и стратегия ротации журнала.
- Односерверный SQLite-индекс не должен считаться поисковой платформой для 200 млн файлов только потому, что он устранил монолитный JSON.

## Что осталось для 200–400 млн файлов

1. Обследовать реальное хранилище: число файлов/папок, длины путей, кардинальности
   уровней, права, скорость обхода и источник изменений. Зафиксировать CPU, RAM,
   NVMe и бюджет резервного хранения. Этих параметров нет в исходных MD.
2. Подключить промышленный источник полного снимка и упорядоченных событий со
   стабильными ID и watermark. Outbox собственных перемещений уже реализован;
   изменения посторонними процессами требуют отдельного адаптера и сверки.
3. Проверить восстановление operational SQLite, import journal, manifests и
   OpenSearch snapshots в согласованной точке. Подтвердить RPO/RTO. Разделение
   процессов на одном сервере не обеспечивает отказоустойчивость хоста.
4. Для уровней с более чем 10 000 вариантами согласовать с frontend пагинацию
   фасетов. Адаптер сейчас отклоняет такой ответ, не скрывая усечение.
5. Пройти рост корпуса и длительные нагрузки на целевой конфигурации: 50 разных
   пользователей, уникальные широкие запросы, параллельная индексация/аудит,
   холодный page cache, рестарты, заполнение диска и восстановление. Перенос
   operational DB на PostgreSQL нужен только при подтверждённом ограничении
   её записи; сотни миллионов поисковых документов уже вынесены из неё.

### Как перенести контракт в поисковый движок

Адаптер OpenSearch 3.8.0 сохраняет канонические токены в пяти полях и позиции слов для фраз. Каждое слово получает фиксированную оценку exact/prefix через `constant_score`; `dis_max` с `tie_breaker=0` выбирает максимум полей. Между словами и фразами используется AND с суммой оценок. Эти строительные блоки описаны в документации [constant score](https://docs.opensearch.org/latest/query-dsl/compound/constant-score/) и [disjunction max](https://docs.opensearch.org/latest/query-dsl/compound/disjunction-max/); эквивалентность проверяется golden-тестами против реального движка на нескольких шардах, включая Unicode и все сортировки.

Естественные ключи сортировки рассчитываются при записи, маркеры фильтруются по ID, данные пользователя и корня проверяет API. Exact total, полнота фасетов и ошибки частично отказавших shards проверяются независимо: нельзя возвращать частичный ответ как полный. Публикация связывает root/schema/ranking version и позицию журнала изменений; API читает одну закреплённую версию. Адаптер подключён к API; потоковый импорт поддерживает полные manifests и упорядоченные дельты. Подключение промышленного источника изменений остаётся необходимым.

### Предварительный бюджет индекса

Измеренный формат занимает около 3,8 KB на файл. Простое умножение даёт около **758 GB на одно поколение из 200 млн записей**; старое и новое поколения плюс одна копия — около **2,3 TB**, ещё без staging, WAL, временных результатов, ОС и эксплуатационного запаса. Это расчёт ёмкости именно текущего синтетического SQLite-формата, а не прогноз размера OpenSearch или рекомендуемая конфигурация сервера. Более длинные пути и многочисленные маркеры увеличат объём; нормализация повторяющихся полей может уменьшить его. Задержку запросов таким умножением оценивать нельзя.

### Почему полный обход не обеспечивает свежесть

Расчёт ниже относится к 200 млн записей; 100–400 млн — лишь чувствительность к среднему размеру файла, не измеренная кардинальность.

| Скорость полного обхода | Время одного обхода 200 млн файлов | Время первичной индексации при той же скорости |
|---|---:|---:|
| 1 000 записей/с | 55,6 ч | 55,6 ч |
| 10 000 записей/с | 5,56 ч | 5,56 ч |
| 100 000 записей/с | 33,3 мин | 33,3 мин |

Чтобы обновить полную картину за пять минут, потребовалось бы 666 667 записей/с. Поэтому требование свежести нельзя строить на постоянном полном обходе: для него нужен долговечный журнал изменений и периодическая сверка из шага 3.

Воспроизведение существующих локальных регрессий из корня репозитория:

```sh
uv run python backend/benchmarks/scale.py --api --records 10000 --repeats 10
uv run python backend/benchmarks/indexer.py --files 1000000 --sqlite
uv run python backend/benchmarks/million.py --records 1000000 --data-dir /tmp/wiseway-million
uv run python backend/benchmarks/million.py --phase query --records 1000000 --data-dir /tmp/wiseway-million --clients 50 --requests 250
uv run python backend/benchmarks/read_paths.py --audit-events 50000 --batches 200 --attempts 50
uv run python backend/benchmarks/stress.py --accounts 50 --rounds 50 --varied-queries
```

Стенды создают отдельные синтетические данные и не открывают рабочую `.wiseway`.
