# Техническое задание: иерархический поиск и ручная сортировка файлов

Редакция 2.0 от 09.09.2026. Команда: Frontend + Backend + QA/инициатор. Первая поставка: внешняя демоверсия на полностью синтетических данных. Указанные далее MUST / «обязан» означают критерий приёмки текущего этапа, если явно не указан следующий этап.

## 1. Назначение

Сервис помогает опытному сотруднику находить файлы по известным признакам их размещения: диск, компания, проект, год, раздел и последующие папки. Основная проблема — длинные пути и большое число объектов; файлы обычно уже разложены правильно. Сотрудник должен найти конкретный файл или всю подходящую ветку, увидеть путь и при необходимости скопировать его.

Второй обязательный процесс — физическое раскладывание небольшого потока новых файлов из входящих папок по заранее существующим целевым папкам. Правила задают пользователи. Сортировка запускается вручную, работает по точным маскам, может переименовать файл и учитывает все опубликованные справочники компании.

Поиск работает по **метаданным, имени и пути**, без чтения содержимого DOCX, PPTX, Excel, PDF или изображений. Для этого этапа GPU, OCR и языковые модели не нужны. Поисковый индекс хранит метаданные; весь архив в приложение не копируется.

## 2. Поставка и границы

| Возможность | Внешняя демоверсия — обязательна | Следующий внутренний этап |
|---|---|---|
| Вход, выход, персональная атрибуция | Локальные синтетические пользователи | Корпоративные параметры учётных записей |
| Иерархический поиск и текст по имени/пути | Да, с настоящим сервером и индексом | Проверка на согласованной части реального архива |
| Индексатор | Метаданные синтетической песочницы, первичный обход и изменения | Адаптер реального хранилища, контроль пропускной способности |
| Справочники | Несколько на компанию; черновик, тест, публикация, версии, откат версии | Наполнение реальными правилами внутри контура |
| Сортировка | Ручная, с физическим перемещением синтетических файлов без перезаписи | Проверка реальной файловой семантики и разрешений |
| Нет правила / конфликт правил | Передача в папку ручного разбора с исходным именем | Та же бизнес-логика |
| Занятая цель | Файл остаётся во входящих, видна причина | Отдельно подтверждённая замена с резервом |
| Технический карантин | Да; ручной возврат во входящую папку | Проверка на реальном хранилище |
| Откат опубликованного справочника | Да, как новая версия | Та же логика |
| Отмена выполненного перемещения файла | Нет | Обычная компенсация и полный откат замены |
| Резерв, физическое удаление, его очистка | Нет | По согласованной политике и отдельным правам |
| Журнал действий | Общий бизнес-журнал, связь с пользователем и файлами | Корпоративные сроки хранения и системный аудит |

Не входят: карта и геопоиск; поиск по содержимому; ИИ-классификация; загрузка через браузер; открытие/скачивание/редактирование файлов из поиска; сохранённые запросы; экспорт; автоматическая сортировка по расписанию; регулярные выражения и сложный конструктор условий; глобальный поиск одновременно по всем дискам; отдельное приложение для ручного разбора проблемных файлов.

Первая поставка должна включать **обе функции**. Интерфейс на имитации API — промежуточная демонстрация, а не завершённая поставка.

## 3. Роли и ответственность

| Участник команды | Основной результат | Владеет | Проверяет |
|---|---|---|---|
| Frontend | Интерфейс и общий внешний контракт | OpenAPI, примеры запросов/ответов, типы клиента, имитация API, UI, браузерные тесты | Совместимость сервера с потребностями UI |
| Backend | Рабочий сервер и безопасная сортировка | БД, индекс, API-обработчики, сессии, справочники, очередь, файловые адаптеры, сборка | Реализуемость контракта, серверные ограничения |
| QA / инициатор | Проверяемая и принятая демоверсия | Эталонные результаты, сценарии, реестр ошибок, независимая приёмка | Контракт, интерфейс, реальный API, итоговое поведение |

Владелец контракта — **Frontend**. Бэкенд не меняет поля ответа по своему усмотрению. Фронтенд не переносит в браузер выбор правил, вычисление счётчиков, проверку занятости пути или решение о перемещении. QA не становится третьим разработчиком продукта; он может писать автоматические проверки и генераторы тестовых данных.

Роли пользователей приложения отличаются от ролей разработчиков:

- `WORKER`: единый доступ ко всем опубликованным корням, очередям компаний, справочникам и бизнес-журналу; создание/редактирование/тест/публикация справочников, ручной запуск, возврат из карантина.
- `ADMIN`: те же рабочие действия плюс настройка конфигурации и пользователей. В демо достаточно воспроизводимого серверного создания/блокировки тестовых пользователей; отдельный экран управления аккаунтами не обязателен.

Назначенный сотрудник собирает справочники организационно; это не исключительное право редактирования. Инициатор утверждает начальную схему уровней и результат по отзывам тестовой группы.

## 4. Экраны

| Экран | Содержание и действия |
|---|---|
| Вход | Логин, пароль, ошибка, состояние отправки |
| Поиск | Диск, строка поиска, последовательные уровни над таблицей, счётчики, файлы, копирование пути |
| Справочники | Выбор компании; список, черновик, таблица правил, тест, публикация, версии, откат |
| Очередь сортировки | Компания, счётчики, статусы, выбор файлов, предварительный расчёт, «Рассортировать», прогресс и итог |
| Карантин | Файлы с подтверждёнными техническими ошибками, причина, исходный путь, возврат |
| Журнал | Период, пользователь, тип/результат операции, имя/путь; детали партии и файлов |

Первый экран после входа — пустой «Поиск». Отдельная сводная панель не нужна. Для каждого экрана обязательны состояния загрузки, отсутствия данных, успеха, ошибки и недоступного действия; для поиска и предварительных расчётов — устаревшие данные. Кнопки с незаполненными обязательными полями объясняют причину недоступности.

## 5. Вход и состояние пользователя

| ID | Требование |
|---|---|
| AUTH-01 | Вход по локальному логину и паролю. Успешный ответ устанавливает серверную сессию и сообщает неизменяемый ID пользователя, логин, отображаемое имя и роль. |
| AUTH-02 | Все пользовательские API, кроме входа и технической проверки доступности, требуют активной сессии. Сервер определяет автора по сессии, а не по присланному `actor_id`. |
| AUTH-03 | Выход, истечение сессии или блокировка пользователя прекращают дальнейшие запросы от его имени. Клиент очищает поисковое и операционное состояние и показывает вход. Уже принятая партия продолжает выполняться с первоначальным автором. |
| AUTH-04 | Пароли хранятся только стойкими солёными хешами. Пароль разрешён во входящем запросе авторизации, но не возвращается в ответе, не пишется в журнал, URL или browser storage. Секреты доступа к хранилищу остаются только на сервере. |
| AUTH-05 | Нет саморегистрации и сброса через почту. Демо создаёт минимум двух рабочих пользователей для конкурентных тестов и администратора; реальные пароли/аккаунты не используются. |

## 6. Поиск

### 6.1. Навигация и запрос

| ID | Требование |
|---|---|
| SRCH-01 | Сначала выбирается один опубликованный диск. Без него поиск недоступен. Только выбранный диск без текста и маркеров не выводит все файлы: таблица пуста, показана подсказка и первый доступный уровень. |
| SRCH-02 | Все уже выбранные уровни расположены над таблицей. Изначально виден только следующий доступный список; выбор одного значения открывает следующий. На каждом уровне одно значение. Можно остановиться после любого уровня и увидеть все соответствующие файлы. |
| SRCH-03 | После выбора диска известный признак глубокого уровня можно сразу ввести в общую строку. Это не требует выбора родителей; выпадающие списки продолжают работать последовательно. |
| SRCH-04 | Текст и выбранная цепочка объединяются через AND. Значения следующего уровня и их точные счётчики рассчитаны по тому же множеству, что и выдача. Нулевые значения скрываются. |
| SRCH-05 | Показываются фактические названия папок. Разные написания, в том числе регистр, остаются отдельными значениями; справочник расшифровок сокращений для поиска не создаётся. |
| SRCH-06 | Списки поддерживают поиск по началу названия без учёта регистра. Порядок — естественный: числовые фрагменты сравниваются как числа, затем русская регистронезависимая сортировка; при равенстве — исходная строка и ID. Браузер сохраняет порядок сервера. |
| SRCH-07 | Обычные слова обязательны все и совпадают по началу токена без учёта регистра. Разделители: пробел, дефис, подчёркивание, точка, оба слеша, переход между буквой и цифрой. Нет исправления опечаток, синонимов или нечёткого поиска. |
| SRCH-08 | Двойные кавычки задают соседние полные токены в указанном порядке в одном поле. `"atlas main"` соответствует `Atlas-Main`, но не `Atlas Final Main` и не `Atlas-Maintenance`. Префикс внутри кавычек не применяется. |
| SRCH-09 | Автозапуск после пробела, завершившего слово. Enter и «Найти» применяют завершённый текст сразу. Незакрытая кавычка не запускает поиск и показывает «Закройте кавычку». Одинаковое применённое состояние повторно не запрашивается. |
| SRCH-10 | При смене папки текст сохраняется, все дочерние уровни и ручная сортировка очищаются. При смене диска сбрасываются текст, маркеры, выдача и сортировка. При изменении текста ручная сортировка сбрасывается. |
| SRCH-11 | «Очистить строку» сохраняет диск и маркеры. «Сбросить всё» удаляет весь выбор, включая диск. При нулевой выдаче условия сохраняются; они не ослабляются автоматически. |

### 6.2. Результаты и состояния

| ID | Требование |
|---|---|
| SRCH-12 | В выдаче только файлы. Поля: имя, полный отображаемый путь, распознанные уровни, расширение, `size_bytes`, дата-время изменения, состояние соответствия структуре. Папки служат для навигации. |
| SRCH-13 | При тексте порядок по релевантности; только маркеры — по полному пути. Ручная сортировка: имя сначала ASC, изменение сначала DESC, размер сначала DESC; повтор меняет направление. Равенство разрешается полным путём ASC и ID ASC. |
| SRCH-14 | Сервер возвращает точное общее число и первые N файлов. При превышении N — обычный успешный ответ `limited=true` и просьба уточнить запрос. У поисковой таблицы нет пользовательских страниц, бесконечной прокрутки или автодогрузки. |
| SRCH-15 | Путь полностью виден в одной строке без многоточия; таблица имеет горизонтальную прокрутку. «Копировать полный путь» копирует только отображаемый путь и кратко подтверждает действие. Файл не открывается. |
| SRCH-16 | Размеры: десятичные B/KB/MB/GB/TB с делителем 1000, максимум один дробный знак. Дата: ДД.ММ.ГГГГ ЧЧ:ММ в едином настроенном часовом поясе. Сервер хранит время в UTC и размер как точное целое число байтов. |
| SRCH-17 | Ошибка обновления сохраняет последнюю успешную выдачу с явной пометкой устаревания и временем. Она не выдаётся за результат новых условий. Ответ на более старый запрос не заменяет результат текущего выбора. |
| SRCH-18 | Переход между разделами сохраняет поиск в памяти вкладки. Перезагрузка, закрытие вкладки и смена пользователя его очищают. Запросы/пути не сохраняются в URL, localStorage, sessionStorage или журнале запросов. |

### 6.3. Схема, индекс и отклонения

| ID | Требование |
|---|---|
| SRCH-19 | Схема уровней версионируется и задаётся технической конфигурацией. Демо использует вымышленную схему; приложение не зашивает постоянное число уровней. Поддерживаются общий префикс и варианты хвоста по компании/проекту, обязательные уровни и необязательный конечный суффикс. |
| SRCH-20 | Разбор останавливается на первом отклонении без перестановки и угадывания уровней. Файл остаётся доступен по имени/пути и распознанным родителям. «Не распознано» идёт последним со своим счётчиком; его выбор завершает каскад. |
| SRCH-21 | В контекстном представлении отклонений: корень, имя, путь, распознанные родители, первый проблемный уровень, понятная причина, дата-время. Нет отдельной очереди исправления и ручного закрытия. После исправления файла и обновления индекса отклонение исчезает. |
| SRCH-22 | Индексируются обычные файлы любых расширений, без расширения и нулевого размера; содержимое не читается. Служебные входящие папки, ручной разбор, карантин и технические временные файлы исключаются из пользовательского поиска по конфигурации. |
| SRCH-23 | Первичный обход имеет прогресс, счётчик объектов, checkpoint и прогноз окончания после достаточного замера. Корень становится доступен после полного обхода и сверки, по команде технического специалиста. |
| SRCH-24 | Создание, изменение, переименование, перенос и удаление обновляют индекс. Старое имя/путь больше не участвуют в поиске. Периодическая сверка метаданных дополняет обнаружение изменений; полный повторный разбор содержимого не требуется. |
| SRCH-25 | Один ответ поиска, total и все facets читаются из одного опубликованного поколения индекса. Фоновое обновление не прерывает чтение предыдущего завершённого поколения. |

Пример **только вымышленной схемы демо**: `Раздел → Компания → Проект → Категория → [Подкатегория]`. Значения: раздел `Archive`; компании `Atlas`, `Nova`; проекты `Orion_2031`, `Polaris_2030`; категории `Reports`, `Data`; необязательный конечный уровень `Text`, `Maps`. Сегмент проекта остаётся одним видимым маркером; его название и год извлекаются в служебные поисковые признаки. Для проверки другого хвоста у Nova между проектом и категорией добавляется обязательный уровень `Area` со значениями `North`/`South`. Эти значения описываются конфигурацией и тестами, а не условиями в компонентах UI. Они не являются предполагаемой схемой компании заказчика.

Синтетический корпус включает файлы PDF/XLSX/DOCX/PPTX/PNG, обычный файл без расширения, нулевой файл, значения разного регистра и ошибочные уровни. QA фиксирует точные IDs и ожидаемые выборки отдельно; совпадение только в содержимом не должно делать файл результатом поиска.

## 7. Справочники сортировки

| ID | Требование |
|---|---|
| DICT-01 | У компании несколько независимых справочников: стабильный ID, уникальное в компании название, описание, один общий черновик, история неизменяемых версий, одна активная версия. Компании и входящие источники задаются конфигурацией. |
| DICT-02 | Все опубликованные версии всех справочников компании образуют единый действующий набор правил. Оператор не выбирает отдельный справочник для запуска сортировки. |
| DICT-03 | Правило содержит ID, приоритет 1–1000, поле BASENAME или RELATIVE_PATH, простую маску, целевой существующий каталог и полное фиксированное новое имя без расширения. Меньший приоритет применяется первым. |
| DICT-04 | Маска сопоставляется со всем выбранным полем, без учёта регистра; `*` — любое число символов, `?` — один. Для подстроки нужны `*` с обеих сторон. В RELATIVE_PATH wildcard может пересекать разделители. `**`, escape wildcard, regex, скрытый OR и переход на другое поле не поддерживаются. |
| DICT-05 | Итоговое имя — фиксированная основа + последний исходный суффикс расширения с исходным регистром. `archive.tar.gz` даёт `.gz`; `.env`, `README`, `name.` расширения не имеют. Непустая основа не содержит разделителей или недопустимых символов. |
| DICT-06 | Среди совпавших правил минимального приоритета разные итоговые цели дают конфликт. Одинаковая цель конфликтом не является; атрибуция выбирается стабильно по ID справочника и правила. Приложение не создаёт целевые каталоги. |
| DICT-07 | Цель выбирается из допустимых каталогов или вводится полным отображаемым путём вручную. В демо разрешён только синтетический префикс `DEMO:/SandboxRoot`; сервер разрешает его в логический ID и относительный путь. Произвольный путь компьютера не принимается. |
| DICT-08 | Сохранение требует текущую ревизию черновика. Изменения коллеги не перезаписываются: конфликт возвращается в UI с предложением перечитать черновик, сохранив несохранённый текст в памяти для сравнения. |
| DICT-09 | Тест черновика рассчитывается без перемещений на всех READY-файлах компании, независимо от фильтров UI. Проверяемый черновик заменяет только свою версию в полном опубликованном наборе. |
| DICT-10 | Любой конфликт правил блокирует публикацию. «Нет сценария» не блокирует, но требует явного подтверждения конкретного результата теста. Публикация требует свежий тест, ревизию, полный набор версий и комментарий 1–500 символов. |
| DICT-11 | Публикация создаёт неизменяемую версию. Откат справочника создаёт новую версию из выбранной старой, проходит текущий тест и публикацию. Прежняя история не редактируется. |
| DICT-12 | Изменение правил делает ещё не принятые preview устаревшими. Уже принятая партия сохраняет зафиксированные версии и планы; новые правила применяются при следующем запуске. |

## 8. Очередь и ручной запуск

| ID | Требование |
|---|---|
| QUEUE-01 | Отдельные входящие источники связаны с компанией. Сервер рекурсивно обнаруживает обычные файлы и проверяет завершение поступления: DISCOVERED → WAITING_READY → READY. Изменение/переименование требует новой проверки готовности. |
| QUEUE-02 | Сначала выбирается компания; режима всех компаний нет. Общая очередь доступна всем рабочим пользователям. Счётчики «Готовы», «В обработке», «Требуют внимания» вычисляет сервер; подробный статус выбирается одним фильтром. |
| QUEUE-03 | Один файл, несколько отмеченных файлов или «Все подходящие» фиксируются серверным снимком IDs и ревизий. Нельзя подменять полный набор текущей страницей браузера. Новые поступления после снимка в него не включаются. |
| QUEUE-04 | Предварительный просмотр необязателен. Доступны «Проверить» и немедленное «Рассортировать»; в обоих случаях сервер выполняет расчёт и проверку перед записью. Нажатие кнопки — обязательный ручной триггер. |
| QUEUE-05 | Preview показывает исходные имя/путь, компанию, справочник/версию/правило, итоговое имя/путь, прогнозируемый результат и причину. Прогноз не является выполненной операцией. Для занятой цели доступно сравнение метаданных двух файлов. |
| QUEUE-06 | Изменение источника, состава правил, цели или истечение preview не допускает исполнение старого плана. Сервер возвращает STALE_PREVIEW до создания партии; UI предлагает пересчитать. |
| QUEUE-07 | Сервер атомарно закрепляет файл за попыткой. При пересечении запусков второй получает ALREADY_PROCESSING для занятых элементов; остальные безопасные элементы продолжаются. |
| QUEUE-08 | Принятый запуск возвращает batch ID, инициатора, время, статус, прогресс, пофайловые результаты. Обновление страницы не теряет принятую партию; она доступна в списке запусков и журнале. |
| QUEUE-09 | Повтор того же запроса с тем же ключом идемпотентности возвращает ту же партию, без повторных перемещений. Новый ручной повтор после исправления создаёт новый ключ и новую попытку. |
| QUEUE-10 | Ошибка одного файла не останавливает безопасные файлы. Смена компании очищает выделение и preview, но не отменяет принятые партии. Пользовательская отмена выполняющейся партии не входит в демо. |

## 9. Файловые операции

| ID | Требование |
|---|---|
| FILE-01 | Штатная операция переименовывает и атомарно перемещает файл без перезаписи в существующий допустимый каталог. Для демо все каталоги песочницы находятся в одной файловой системе; неподтверждённый межфайловый перенос не заменяется незаметным copy/delete. |
| FILE-02 | Занятая цель: исходный и существующий файлы остаются нетронутыми; статус REQUIRES_DECISION, причина TARGET_OCCUPIED. В демо нет кнопки замены. После ручного освобождения пути нужен новый явный запуск. |
| FILE-03 | Несколько выбранных файлов, рассчитанных на одну итоговую цель: каждый участник этой коллизии получает TARGET_OCCUPIED и остаётся во входящих. Порядок обработки не выбирает «победителя». Это правило демо для предсказуемой приёмки. |
| FILE-04 | NO_SCENARIO и RULE_CONFLICT после запуска переносят файл в заранее существующую плоскую папку ручного разбора своей компании. Сохраняется фактическое исходное имя целиком. Эти причины не являются техническим карантином. |
| FILE-05 | Если имя в ручном разборе занято, файл остаётся во входящих с MANUAL_REVIEW_NAME_OCCUPIED. Нет суффикса, автоматического нового имени, замены или создания подпапок. |
| FILE-06 | Технический сбой после принятого запуска: если источник достоверно найден и доступен, сервер пытается переместить его в карантин без перезаписи. Если положение файла неоднозначно или карантин недоступен, фиксируется RECOVERY_REQUIRED; успех карантина не выдумывается. |
| FILE-07 | Возврат из карантина выполняется вручную с комментарием 1–500 и проверкой исходного входящего пути. Если он занят, ничего не перемещается. Успех возвращает WAITING_READY; сортировка автоматически не запускается. |
| FILE-08 | Перед каждой записью проверяются границы песочницы, типы файлов/каталогов, идентичность источника и свободная цель. Ссылки и выход за разрешённый корень не допускаются. Браузер передаёт логические IDs и относительные значения. |
| FILE-09 | Намерение и фазы попытки сохраняются до файловой операции. После сбоя сервер восстанавливает однозначно доказанный исход; неоднозначный требует ручного разбора. Повторный старт не выполняет неподтверждённую операцию вслепую. |

После подтверждённой передачи в папку ручного разбора ответственность сортировщика завершена. Отдельный UI её разбора не нужен; сотрудники работают с папкой привычными средствами. Внешние последующие действия не приписываются приложению.

## 10. Журнал

| ID | Требование |
|---|---|
| AUD-01 | Журнал добавляет неизменяемые события: время UTC, ID, автор, тип/результат, request ID, company/dictionary/version/batch/attempt/item по применимости, исходное и итоговое логическое размещение, причина. |
| AUD-02 | Сохраняются создание/сохранение/тест/публикация/откат справочника, принятие партии, пофайловые результаты, карантин/возврат. Вход/выход и административные события имеют отдельную системную категорию. |
| AUD-03 | Поиск, навигация, просмотр и копирование пути не создают бизнес-событий. Технические логи не содержат паролей, полного тела запросов, поискового текста или физических путей. |
| AUD-04 | Рабочие пользователи видят общий бизнес-журнал. Фильтры: период, автор, тип, результат, имя/отображаемый путь. По умолчанию текущий день в настроенном часовом поясе. Порядок: occurred_at DESC, event_id DESC. |
| AUD-05 | В журнале есть «Показать ещё» по непрозрачному курсору до 100 записей и индикатор новых событий не позднее 60 секунд. Это отдельная лента; запрет страниц поисковой выдачи на неё не распространяется. Экспорта нет. |

## 11. Архитектура и технические границы

```text
Frontend → клиент, сгенерированный из OpenAPI → HTTP API
  → поиск / справочники / очередь / аудит
  → БД служебных данных + специализированный индекс + файловые адаптеры
```

Frontend работает с браузерным контрактом, Backend — с реализацией и файловой системой. Один логический репозиторий. Общие DTO описаны в OpenAPI; независимые ручные копии моделей на клиенте запрещены. Серверные модели могут быть внутренними, но обязаны соответствовать контракту на границе API.

Порты серверной части: чтение метаданных, изменение файлов, поисковый индекс, служебная БД, пользовательская идентичность, аудит, обнаружение изменений. Физические пути определяются только серверной конфигурацией адаптера. Демо использует генерируемую песочницу; следующий внутренний адаптер заменяет её без переписывания правил и экранов.

Рабочая технологическая основа для оценки: React + TypeScript, Python + FastAPI, PostgreSQL, специализированный поисковый индекс. Это инженерное предложение, а не утверждение об установленных компонентах. Точные версии и конкретный индекс команда фиксирует в ADR и lock-файлах при подготовке рабочей сборки. Переход на иной стек не меняет семантику API.

## 12. Нефункциональные требования и параметры демо

| ID | Требование |
|---|---|
| NFR-01 | Русские подписи и ошибки, управление клавиатурой, видимый фокус, подписи полей, читаемая таблица длинных путей. Целевая среда демо — настольный браузер, от 1280×720; при меньшей ширине допустима прокрутка. |
| NFR-02 | Воспроизводимая сборка из чистой копии: закреплённые зависимости, миграции БД, генератор синтетики, инструкция запуска и тестирования. Нет подключения к корпоративным данным из внешней демо. |
| NFR-03 | На объявленном тестовом стенде фиксируются число файлов, кардинальности уровней, аппаратные ресурсы и время ответов. Цель: p95 типового поиска ≤2 секунд, широкая ветка ≤5 секунд. Демо не доказывает этот норматив на реальном архиве. |
| NFR-04 | Обновления метаданных в опубликованном разделе видны ≤5 минут. Первичная индексация имеет прогресс, продолжение после сбоя и измеренный прогноз; произвольный срок полного обхода не назначается. |
| NFR-05 | Сессия серверная; auth-cookie HttpOnly и SameSite, Secure при HTTPS. Запросы записи защищены от CSRF, ответы пользовательских API имеют Cache-Control: no-store. Демо на loopback может работать по HTTP; внутренний доступ требует HTTPS. |
| NFR-06 | Поиск сохраняет доступ к завершённому поколению при обновлении индекса. Перезапуск не теряет справочники, принятые партии, журнал и известные результаты файловых операций. |
| NFR-07 | Сортировка выдерживает два одновременных запуска на пересекающемся наборе без двойного перемещения. UI не зависает на длительном задании; прогресс и результат получаются повторными запросами. |

Следующие значения — **новые настройки только демо**, а не якобы согласованные параметры внутренней инфраструктуры. Их фиксирует команда в конфигурации и тестах; изменение требует обновить общие примеры:

- Два синтетических проекта за два синтетических года как минимум, две компании, минимум два справочника у одной компании; схема проверяется и на вариантах глубины.
- N выдачи = 100, отдельный тестовый профиль N = 10; набор обязан содержать больше N совпадений. Полный норматив N для эксплуатации определяется замером.
- Максимум одной партии = 1000 файлов, ограничение показывает сервер; превышение отклоняется целиком, без тихого усечения.
- Снимок выбора, preview и результат теста справочника действуют 5 минут и инвалидируются раньше при изменении зависимостей. Ключи идемпотентности принятых партий сохраняются вместе с партиями.
- Период проверки поступления = 5 секунд; минимум два одинаковых наблюдения размера/mtime и отсутствие признака незавершённой поставки. Это эвристика демо, не доказательство окончания записи на неизвестном хранилище.
- Опрос активной партии = 1 секунда с замедлением при ошибках; не создавать параллельные одинаковые poll-запросы. Опрос новых событий журнала = 30 секунд.
- Часовой пояс отображения демо = Europe/Moscow; сервер возвращает его в app-config. Не считать этим закрытым вопрос корпоративного пояса.
- Сессия демо: 8 часов абсолютного времени, 30 минут бездействия; парольные ограничения демо задаются отдельно от будущей политики компании.

## 13. Следующий внутренний этап — сохранить при проектировании

Будущий массив: ориентировочно 93 ТБ физически после сжатия 2,1, около 195 ТБ логически. Эти числа — исходная оценка, не результат обследования. Для мощности индекса важнее число файлов/папок, длина путей, число значений уровней и скорость обхода метаданных. GPU A100 не нужен для заявленного metadata-only MVP; требуются отдельные CPU/RAM/SSD-ресурсы.

Плановая аудитория — 30–40 сотрудников; внутренний нагрузочный критерий — до 50 одновременно. Работа в согласованные рабочие часы с плановыми окнами. Восстановление служебных компонентов ≤4 рабочих часов, потеря служебных данных ≤1 часа. До согласования срока хранения автоматическое удаление журнала/резерва отключено.

До реального пилота уточняются: фактический CIFS/SMB и версия; ОС и права; атомарность переносов внутри/между корнями; стабильность файловых ID и case/Unicode-семантика; канал изменений и расписание сверки; объекты и скорость metadata обхода; корпоративная схема уровней; допустимые ресурсы; часовой пояс, аккаунты, резервное копирование и перенос зависимостей. Сисадмины обеспечивают установку компонентов во внутренний контур после внешней демо по обоснованным запросам инициатора.

Внутренний этап отдельно реализует замену с резервом и обратные перемещения с проверкой обоих путей, комментарием и новой записью аудита. Для обычного поиска источник читается без записи; права сортировщика ограничиваются согласованными входящими и целевыми каталогами.

## 14. Приёмка и комплект результата

Демо принимается, когда один новый участник по README запускает приложение, входит, находит файлы по иерархии/тексту, создаёт и тестирует справочник, публикует его, вручную сортирует синтетические файлы, видит физический результат и журнал. Отдельно проходят коллизии, устаревшие планы, конкуренция, техническая ошибка и возврат.

Обязательны: OpenAPI; сгенерированный клиент; имитация API; сервер и миграции; индексатор; генератор и эталонные результаты; компонентные/серверные/контрактные/сквозные тесты; отчёт QA с указанием commit и среды; инструкция запуска, резервирования служебных данных и переноса. Каждый проваленный сценарий имеет зарегистрированный дефект; потеря данных, перезапись, двойная операция, неверная выдача/счётчики и неработающий основной сценарий блокируют приёмку.

План по ролям — `06_EXECUTION_PLAN.md`; детальные действия — `03_FRONTEND.md`, `04_BACKEND.md`, `05_QA.md`; сценарии — `07_ACCEPTANCE_MATRIX.md`. Контракт `02_API_CONTRACT.md` определяет названия полей и поведение API. Изменение функционального требования обновляет связанные API, тесты и ролевые задачи в одном согласованном изменении.
