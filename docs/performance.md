# Производительность и рост архива

Целевой будущий объём — 100 тысяч–1 миллион файлов на одном Linux-сервере, до 50 пользователей. Текущая поставка ещё не подтверждает работу на этом объёме: она использует синтетическое хранилище и ограниченный обход файловой системы.

## Выполненные изменения

- Поиск начинает с наиболее избирательных списков совпадений. Редкий или отсутствующий запрос больше не создаёт таблицу оценок для всего корня. Фасеты пустого запроса подготовлены вместе с поколением индекса.
- Естественный порядок путей вычисляется один раз на поколение. Для ограниченного ответа выбираются лучшие строки; весь результат повторно не сортируется. Счётчики, правила релевантности и направления сортировки сохранены.
- Четыре документа индекса делят общий бюджет 32 MiB сериализованных данных: один корень может использовать свободную часть бюджета. Это убирает прежний обрыв кэширования на 8 MiB, не увеличивая суммарный бюджет. Python-объекты и поисковые структуры занимают дополнительную память; 32 MiB не являются лимитом RSS.
- Checkpoint индекса записывает только очередную порцию до 100 файлов. Объём записей растёт линейно; прежняя реализация на каждом шаге переписывала весь накопленный результат. Сохранены проверка метаданных при продолжении и атомарная публикация; параллельные индексаторы координируются файловой блокировкой.
- Журнал читает страницы через индекс SQLite и курсор последней строки. Снимок сохраняет границу последовательности, владельца, фильтры и TTL вместо копии всего журнала. Новые события не попадают в старые страницы; микросекунды и истёкшие курсоры проверены отдельно. Polling и список авторов также не декодируют весь журнал.
- Список партий загружает связанные попытки группами. Частичные индексы БД ускоряют выборку попыток партии и очереди компании; счётчики и generation используют одну согласованную выборку очереди.

Новые индексы создаются миграциями 004/005. Перед обновлением нужна полная копия. На большом журнале построение индекса занимает время: выполните миграции административной CLI до запуска API/worker и планируйте окно обслуживания.

## Локальные замеры

Сравнение с `60154d3`, macOS ARM64, Python 3.11.5, одинаковые синтетические корпуса. Поиск: медиана 10 запросов после одного прогрева. Это измерения одного процесса без 50 одновременных клиентов.

| Сценарий | До | После |
|---|---:|---:|
| API/SQLite, 10 000 записей, редкое совпадение | 176,81 мс | 2,86 мс |
| API/SQLite, 10 000 записей, широкий поиск | 235,87 мс | 11,77 мс |
| Подготовленный алгоритм, 100 000 записей, широкий поиск | 362,80 мс | 152,52 мс |
| Перестроение индекса 9 505 файлов, один запуск | 5,774 с | 0,469 с |
| Список 200 партий / 10 000 попыток, сервис/SQLite | 3 164,35 мс | 27,76 мс |
| Проверка новых событий в журнале из 50 000 записей, сервис/SQLite | 186,40 мс | 0,44 мс |

API-стенд включает ASGI, SQLite и валидацию ответа, но не настоящий TCP или обход 10 000 файлов: метаданные помещены в отдельную тестовую БД. Первый холодный запрос на этом корпусе после изменения занял около 167 мс. Стенд алгоритма на 100 000 записей намеренно обходит производственный предел prepared-индекса; его результат не доказывает готовность всего backend на 100 000 файлов. Пиковый RSS процесса этого стенда — около 600 MiB.

Стенд истории измеряет сервисные функции и SQLite, без HTTP/валидации ответа; медиана трёх вызовов. Первая страница журнала из 50 000 событий раньше отклонялась по лимиту 8 MiB снимка, теперь возвращает 100 записей примерно за 1,73 мс. Это устранённый отказ, а не сравнение скорости двух успешных ответов.

Повторная нагрузка через настоящий TCP: 50 разных аккаунтов, 50 клиентов, 12 500 запросов, 3 200 добавленных файлов, 1 000 событий журнала и отдельный worker. Все ответы прошли проверку, API/worker остались живы, в логах не обнаружены SQLite busy и 5xx. p95: типовой поиск 1 378 мс, широкий поиск 1 308 мс, очередь 1 000 мс, журнал 1 932 мс; RSS API после прогона — около 121 MiB. На том же локальном стенде предыдущий прогон давал p95 поиска около 350–386 мс: задержки зависят от состояния общего хоста. Это проверка устойчивости короткого сценария, не подтверждение SLA целевого сервера или миллиона файлов. Сессии созданы до нагрузки, пропускная способность публичного login здесь не измеряется.

Воспроизведение из корня репозитория:

```sh
uv run python backend/benchmarks/scale.py --api --records 10000 --repeats 10
uv run python backend/benchmarks/scale.py --records 10000 100000 --repeats 10
uv run python backend/benchmarks/indexer.py --files 9500
uv run python backend/benchmarks/read_paths.py --audit-events 50000 --batches 200 --attempts 50
uv run python backend/benchmarks/stress.py --accounts 50 --rounds 50 --varied-queries
```

Для сравнения с отдельной копией старого backend первые четыре команды поддерживают `WISEWAY_BENCHMARK_BACKEND=/absolute/path/to/baseline/backend`. Копия должна содержать соответствующий контракт. Все стенды создают временные данные; существующая рабочая база не используется.

## Что требуется для 100 тысяч–1 миллиона

1. Хранить индекс отдельными записями с индексируемыми полями и списками токенов. Сейчас опубликованное поколение — один JSON-документ; его полная загрузка и переписывание становятся основным ограничением памяти и задержки. Увеличение кэша это не решает.
2. Сделать потоковый первичный обход с ограниченной памятью и устойчивым продолжением; затем обновлять только изменённые записи. Публикация поколения должна оставаться атомарной, с периодической полной сверкой для пропущенных изменений.
3. Перенести фильтрацию, счётчики и ограниченную выдачу поиска в постоянный индекс, сохранив токенизацию, prefix/AND/фразы, естественный порядок и фасеты. Готовый поисковый движок нельзя подключить без проверки этих правил.
4. Заменить полные снимки больших очередей/истории партий на ограниченную выборку с сохранением стабильности страниц; предусмотреть рост аудита и политику хранения резервов. В текущем проходе масштабируемые страницы реализованы для журнала.
5. Проверить 100 тысяч, затем миллион файлов на целевом сервере: холодный запуск, 50 клиентов, изменения файлов, запись аудита, перезапуск worker, длительная нагрузка и полное восстановление. Измерять p95, RSS, блокировки БД, место на диске и время восстановления.

Текущий обход сохраняет предел 10 000 записей, глубину 64 и бюджет времени; prepared-индекс не используется свыше 10 000 элементов. Эти ограничения нужно менять вместе с хранением и обходом, после замеров. Выбор СУБД сам по себе не устранит полное чтение JSON и повторные обходы.
