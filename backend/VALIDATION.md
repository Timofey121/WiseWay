## Архитектура и исправления

Для демо подходит модульный монолит: FastAPI обслуживает HTTP, сервисы справочников/сортировки/карантина выполняют бизнес-операции, отдельный worker исполняет сохранённые намерения. SQLite обеспечивает транзакции, журнал и claims; адаптер файловой системы использует дескрипторы каталогов и атомарный rename без перезаписи. Общий OpenAPI остаётся единственным источником wire-схем.

В ходе ревью исправлены:

- Чтение поиска, журнала и очереди удерживало SQLite writer lock. Чтение переведено в отдельные транзакции, сохранение пагинации — в короткую запись; ограничена конкуренция потоков.
- Glob-маски могли вызвать экспоненциальный перебор regex. Используется ограниченный алгоритм сопоставления `*`/`?`.
- Каждая страница дублировала весь результат, истёкшие данные оставались в БД. Введены общие снимки, компактные курсоры, очистка и квоты: 64 снимка/пользователь, до 8 MiB/снимок и 32 MiB суммарно. Одностраничный ответ квоту не расходует. Миграция 002 индексирует метаданные квот/сроков.
- Повторно выполнялись разбор индекса, токенизация и полная проверка одинаковых строк ответа. Добавлены ограниченные кэши точных значений; изменения полей и поколений проверяются повторно. Неизменный индекс не строится заново.
- DESC-сортировки неверно разворачивали вторичный порядок; поиск пропускал нераспознанные части пути; числовая сортировка падала на некоторых Unicode-именах.
- Недоступный дочерний каталог мог дать неполный индекс со статусом CURRENT. Сохраняется последнее полное поколение, выставляется STALE; отказ входящего сканирования виден в status.
- Границы `[from,to)` аудита сравнивались как строки; теперь сравниваются моменты времени. Ранний recovery теперь получает ровно одну запись FILE_ATTEMPT_STARTED перед RECOVERY_REQUIRED.
- Некорректный CSRF-заголовок мог дать 500. Исправлены валидация Origin и ограничение небезопасного HTTP на loopback.
- После rename дополнительно проверяется дескриптор и идентичность цели. Неоднозначный результат сохраняет исходное намерение и RECOVERY_REQUIRED, без автоматического переноса в карантин.
- Внутренние 500 журналируются с request ID и классом ошибки, без текста исключения, traceback, тела, поискового запроса или физических путей.

Авторизация соответствует ТЗ: WORKER имеет общий доступ к опубликованным корням, компаниям, справочникам и BUSINESS-журналу. SYSTEM-события доступны ADMIN. Это общий рабочий контур, а не изоляция арендаторов. Сессия серверная, cookie непрозрачная; в БД хранится её хеш. Пароли — Argon2. В проверенных сценариях обхода этих границ не найдено.

Повторный проход проверил все 64 исходных отслеживаемых файла, затем изменения прошли отдельное ревью и регрессионные тесты. Дополнительно исправлены:

- При сбое индекса сохраняется фактическое время последней успешной синхронизации. FAILED виден даже при сохранённом checkpoint; следующее обновление повторно сверяет его перед продолжением.
- Hard link больше не объединяет разные имена в одну запись: каждый путь получает отдельный ID, файлы независимо достигают READY и обрабатываются. Обычное однозначное переименование сохраняет ID. Старый индекс автоматически перестраивается с новым поколением; неоднозначные одновременные переименования нескольких имён одного inode получают новые ID.
- Обход использует ограниченный итератор: 10 000 записей, глубина 64, суммарные 8 MiB путей, проверка времени 30 с между записями. Превышение не публикует частичный индекс и не помечает прежнюю очередь исчезнувшей. Это пределы локального демо, а не дисковая квота или прерывание зависшего системного вызова.
- Слишком глубокий JSON, UTF-16 вместо UTF-8 и непарные Unicode surrogate отклоняются с 422 без изменения БД; корректные кириллица и emoji сохраняются.
- Запуск и повторный init проверяют маркер Wise Way и завершённый seed базы. Отсутствующая/пустая база не маскируется успешной инициализацией. Прерванная инициализация после seed-транзакции возобновляется без сброса паролей.

Отдельно проверена блокировка после принятия партии: новая HTTP-работа запрещена, сохранённая партия завершается с прежним автором; другой WORKER видит только BUSINESS-события, включая автора, который уже заблокирован. Отмена ранее принятой партии не предусмотрена контрактом.

## Производительность

Измерение одиночного поиска сохранено из предыдущего прохода; оптимизация производительности исключена из повторного ревью. `uv run python backend/benchmarks/search.py`: 3200 добавленных файлов плюс стандартный seed, по 5 прогревочных и 40 измеряемых запросов. Один FastAPI TestClient, без параллельной нагрузки.

| Запрос | Совпадений | p50 | p95 |
|---|---:|---:|---:|
| `benchmark` + Archive/Atlas | 1600 | 14,873 мс | 17,958 мс |
| Широкий `bench` | 3200 | 17,759 мс | 18,655 мс |

Первичный полный scan: 960,99 мс. Измерение относится только к указанному корпусу.

Повторный `uv run python backend/benchmarks/stress.py`: настоящий TCP API, 50 клиентов, 250 запросов, 3200 добавленных файлов, 1000 событий аудита и параллельный worker/indexer. Используются 50 сессий **одного** рабочего аккаунта; это не проверка 50 разных аккаунтов. Клиенты создаются до замера, прогрева запросами нет. Login-rate-limit проверяется отдельно, не этим нагрузочным сценарием.

| Операция | Запросов | p50 | p95 | HTTP |
|---|---:|---:|---:|---|
| `stress atlas` / `stress nova` | 100 | 944,178 мс | **2231,308 мс** | 100 × 200 |
| Широкий `stress` | 50 | 823,748 мс | 911,064 мс | 50 × 200 |
| Очередь | 50 | 444,907 мс | 714,596 мс | 50 × 200 |
| Журнал | 50 | 942,461 мс | 2256,417 мс | 50 × 200 |

Все запросы успешны, таймаутов/5xx/SQLite busy в проверенном логе нет; API и worker остались живы. Время нагрузки — 5,348 с, RSS API после неё — 242704 KiB. Цель p95 типового поиска ≤2 с **не выполнена**; цель широкого ≤5 с выполнена. Скрипт вернул код 1 из-за порога задержки. Предыдущий сопоставимый прогон давал p95 2435,380 мс; разница одного прогона не доказывает ускорение.

## Незакрытые границы

1. **Задержка при 50 клиентах.** Однопользовательский поиск укладывается в цели, смешанная нагрузка — не полностью. Следующий этап: уменьшение стоимости чтения больших JSON-записей/аудита и конкуренции за единственную запись SQLite. Для промышленного объёма нужны отдельное представление поискового индекса, реляционные индексы данных и измерения на целевом стенде.
2. **Сторонний процесс с правом записи в sandbox.** Native rename не умеет атомарно проверить ожидаемый inode. Подменённая ссылка может уже оказаться внутри целевого каталога до проверки результата. Ссылку не открывают, внешний файл не читают/не изменяют, попытку переводят в RECOVERY_REQUIRED. Строгая гарантия «ссылка никогда не перемещается» не выполнена; каталогами во время операций должен владеть только сервис. Для такой модели угроз требуется отдельный проект безопасного приёма/изоляции файлов, а не ещё один `stat`.
3. **Полный продукт и эксплуатация.** Frontend/mock/browser E2E, Linux runtime, Windows, Docker, длительный soak-тест, реальное заполнение диска, backup/restore и промышленная инфраструктура не проверены. CI в репозитории не настроен. История операций и append-only аудит намеренно не очищаются по TTL; рост постоянных данных требует эксплуатационного решения.

Backend-тесты не заменяют независимую приёмку всех параметров исходной матрицы и не означают готовность промышленного сервиса.
