# Поисковый индекс большого архива

OpenSearch 3.8.0 хранит поисковую проекцию отдельно от SQLite с сессиями,
аудитом и файловыми заданиями. API и ранжирование сохраняют контракт 1.1.0.
Это работающий адаптер и потоковый импорт; эксплуатация 200–400 млн записей
пока требует проверки на целевом сервере и подключения источника изменений.

## Подключение

Настройки API, импортера и обслуживания:

- `WISEWAY_SEARCH_URL`: HTTPS origin без пути и credentials в URL.
- `WISEWAY_SEARCH_CA_FILE`: доверенный CA; проверка имени сервера включена.
- `WISEWAY_SEARCH_CREDENTIALS_FILE`: приватный JSON с `username` и `password`.
- `WISEWAY_SEARCH_CACHE_BYTES`: кеш ответов, по умолчанию 8 MiB; `0` отключает.

Секреты передаются файлами, не аргументами команды и не через Git. Используйте
разные учётные записи API и импортера. API нужны чтение и продление PIT только
для `wiseway-*`; импортеру — создание этих индексов, bulk, refresh и управление
PIT. Выдавать API административные права на кластер не требуется.

Для имеющегося приватного TLS-кластера предусмотрен overlay
`infra/opensearch/compose.client.yaml`: задайте `WISEWAY_SEARCH_SECRET_PATH` и
`WISEWAY_MANIFEST_PATH` и добавьте `-f` к обычному Compose-запуску. Запустите
профиль `search`, чтобы `search-maintenance` продлевал снимки раз в минуту.
Общий пример содержит один путь credentials: для разделения ролей переопределите
этот bind mount отдельно для API и CLI/maintenance.

OpenSearch разворачивается и снабжается сертификатами отдельно. Размер heap,
память ОС под page cache, CPU, число шардов, NVMe и резервное хранилище выбираются
по замерам. Один primary без replica соответствует одному серверу и не даёт
защиты от потери диска. Данные кластера не должны лежать на SMB/NFS.

## Первичная загрузка и изменения

Источник предоставляет **завершённый неизменяемый NDJSON-файл**: одна запись на
строку. `item_id` стабилен при переименовании; полный снимок содержит итоговую
запись каждого существующего файла. Источник обязан исключить пропуски и дать
строго упорядоченные дельты после этого снимка.

```json
{"op":"upsert","item_id":"file-123","relative_path":"Archive/Atlas/Orion_2031/Reports/report.pdf","size_bytes":1048576,"modified_at":"2026-09-01T12:00:00Z"}
{"op":"delete","item_id":"file-124"}
```

`delete` допустим только в дельте. Переименование — `upsert` с прежним ID и новым
путём. Содержимое файлов не читается. Значения проверяются до публикации.

```sh
uv run wiseway import-archive archive-root /manifests/initial.ndjson --shards 8 --batch-size 5000
uv run wiseway import-archive archive-root /manifests/delta-001.ndjson \
  --mode delta --base-generation search-GENERATION-FROM-PREVIOUS-COMMAND
uv run wiseway maintain-search --interval 60
```

Число шардов задаётся при полном импорте; изменение требует нового физического
индекса. Значение 8 — начальная настройка, не sizing для 400 млн файлов.
Одновременно работает один импортер. Обычный и SQLite-индексаторы пропускают
переключённые на OpenSearch корни. Остальные входящие файлы и задания продолжают
обрабатываться обычным worker.

Отдельная `archive-import.sqlite3` хранит строки заданий и byte offset, а не
сотни миллионов файлов. По умолчанию пачка ограничена 1 000 записями;
`--batch-size` допускает 1–5 000. Документ и bulk-action кодируются один раз.
Целевой размер пачки — 12 MiB с учётом UTF-8 и разделителей NDJSON, жёсткий
предел запроса — 16 MiB. Одна запись может превысить целевой размер, но не жёсткий
предел. Подготовленная следующая запись не включается в checkpoint предыдущей пачки.
SHA-256 всего исходного файла проверяется при каждом старте; это потоковое
чтение с постоянной памятью. После остановки повторите **ту же команду** с тем
же неизменённым файлом. Подтверждённые пачки пропускаются; неподтверждённая
повторяется с прежними внешними ревизиями. Потеря ответа bulk не создаёт дублей.
Ревизии удаления хранятся как tombstone, поэтому запоздавшая запись не
восстанавливает удалённый файл.

Некорректный источник не публикуется. Исправление: остановить импортер,
`uv run wiseway abort-import archive-root`, затем загрузить новый полный снимок.
Отменённая дельта запрещает дальнейшие дельты в загрязнённый индекс. Старый
опубликованный снимок сохраняется. Старые физические индексы и tombstones
автоматически не удаляются: место и срок хранения контролирует оператор.

## Согласованность и восстановление

После успешных bulk выполняются refresh всех шардов и создание PIT. Только
затем одна транзакция SQLite переключает указатель корня. Поиск, фасеты и
гидратация первых 100 файлов используют этот PIT. Промежуточные изменения
невидимы. Частичный ответ шардов, таймаут или неточный total дают 503.

Публикуйте дельты не чаще одного раза в 30–60 секунд: число одновременно
открытых PIT умножается на число шардов и ограничивается движком.
PIT имеет keep-alive 24 часа; чтения и maintenance продлевают его. Предыдущие
PIT закрываются после двухминутного запаса для начавшихся запросов. После
перезапуска OpenSearch PIT может пропасть. `maintain-search` восстанавливает
его только для полностью подтверждённого физического индекса. При незавершённой
дельте требуется сначала возобновить импорт; при отменённой — полный rebuild.
После восстановления поколение меняется: перед следующей дельтой прочитайте
актуальный `index_generation` через `GET /api/v1/roots`. До восстановления новые
некешированные запросы возвращают 503. При длительном
импорте maintenance ждёт блокировку; это необходимо учитывать при мониторинге.

Кеш ограничен размером и числом записей, живёт 30 секунд, ключ включает поколение
и PIT. Аутентификация/авторизация выполняются до обращения к кешу. Кеш может
кратко обслуживать уже вычисленные ответы при отказе движка; новый запрос
проверяет доступность снимка.

Полный backup теперь должен включать согласованные operational SQLite,
`archive-import.sqlite3`, исходные manifests/дельты и OpenSearch snapshot.
Обычный `wiseway backup` копирует только operational SQLite. Существующий
`infra/scripts/snapshot.py` не сохраняет внешний OpenSearch. Их успешное
завершение **не доказывает восстановимость поискового архива**. Для полного
restore нужно остановить запись/импорт, восстановить согласованные данные,
проверить источник и ревизии, затем восстановить PIT через maintenance.
RPO ≤1 часа и RTO ≤4 рабочих часов ещё надо подтвердить отдельным упражнением
на целевом объёме. Возвращать один старый журнал импорта к более новому индексу
нельзя: нарушится порядок внешних ревизий.

## Проверки и ограничения

Для длительных прогонов с возобновлением, контролем диска и разнообразным
корпусом используйте [capacity-стенд](capacity-testing.md). Новые физические
индексы сортируются по `path_key/path/id`; для фильтруемых `marker_ids` и
`deleted` отключены ненужные doc values. Поля `id`, `path`, `name_key`,
`path_key`, `modified` и `f0`–`f63` сохраняют doc values для сортировки/агрегаций,
но не создают inverted index. Поисковые фильтры используют `t_*`, `marker_ids`
и `deleted`; добавление фильтров по другим полям требует отдельной проверки
mapping и rebuild. Формат документов прежний: старые
индексы продолжают работать, но эти статические настройки получают только при
полном rebuild. Пачки остаются ограниченными по числу записей и байтам.

Приватная схема подготавливается один раз на импорт и один раз при гидратации
снимка поиска. Определение максимальной оценки использует не более одной
score-пробы на компонент запроса (до восьми компонентов); если пересечение
максимумов не заполняет top-k, сохраняется полный точный scorer.

Во время долгого импорта прежний PIT продлевается каждые пять минут. Потеря
старого PIT не блокирует возобновление импорта: чтения остаются недоступны до
публикации нового полного снимка. Незавершённый физический индекс как готовый
снимок не открывается.

Локальная интеграция без TLS разрешена только с явным
`WISEWAY_SEARCH_ALLOW_HTTP=true` и loopback hostname. Отдельный
`infra/opensearch/compose.test.yaml` выключает security **только для синтетических
тестов** и публикует порт исключительно на `127.0.0.1`. CI запускает golden,
Unicode, все сортировки, точные фасеты через несколько страниц, сбои bulk,
публикацию и потерю PIT.

```sh
docker compose -f infra/opensearch/compose.test.yaml up -d --wait
WISEWAY_TEST_SEARCH_URL=http://127.0.0.1:19200 uv run pytest -q backend/tests/test_opensearch.py
WISEWAY_SEARCH_URL=http://127.0.0.1:19200 WISEWAY_SEARCH_ALLOW_HTTP=true \
  WISEWAY_SEARCH_CACHE_BYTES=0 uv run python backend/benchmarks/archive_search.py \
  --data-dir /tmp/wiseway-search-bench --records 1000000
```

Фасеты v1 возвращают все варианты. На одном уровне адаптер допускает не более
10 000 вариантов; превышение даёт 503, без молчаливого усечения. Для больших
кардинальностей нужен согласованный с frontend контракт пагинации фасетов.
Точные total/фасеты могут требовать работы пропорционально числу совпадений.
Для больших наборов отдельно считаются кандидаты и проверяется достижимость
максимальной оценки; когда этот путь не заполняет top-k, работает полный scorer.
Кеш ускоряет повторы, но не гарантирует первый произвольный запрос.

Успешные перемещения нашего worker записывают `search_outbox` в одной транзакции
с результатом и аудитом. `maintain-search` доставляет их ограниченными пачками;
Пачка ограничена 25 000 событиями и 4 MiB исходного JSON. Удаляет из очереди только после публикации. При сбое повторяется сохранённая
пачка с прежней базой и ревизиями. Файловый worker не обращается к сети.

Автоматический SMB/changefeed-адаптер ещё не подключён. Промышленный источник
должен согласовать ID и watermark полного снимка с последующими дельтами,
включая изменения нашего worker; полный снимок не должен терять уже доставленные
события. Импорт дельт — граница интеграции, а не обещание пятиминутной свежести
реального архива. Текущий filesystem/auth runtime остаётся
синтетической песочницей; режим промышленного хранилища и SSO не включены.
