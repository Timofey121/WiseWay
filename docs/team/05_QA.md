# QA: инструкция пользователю и его Codex

Статус документа: требования к будущей проверке синтетического демо. Это не протокол выполненных испытаний и не разрешение работать с реальными файлами. На момент выпуска этого документа наличие реализации, работающих команд и результатов PASS не утверждается.

## 1. Ваша роль и результат

В команде три человека: frontend-разработчик, backend-разработчик и вы — владелец приёмки. Frontend начинает первым и владеет контрактом frontend/backend. Backend проверяет реализуемость контракта и реализует сервер. Вы определяете наблюдаемые ожидаемые результаты, проверяете соответствие продуктовой задаче и принимаете либо отклоняете конкретную сборку по доказательствам.

Ваш Codex помогает готовить синтетические примеры, сценарии, независимые проверки API, протоколы и описания дефектов. Он не должен незаметно исправлять продуктовый код, менять API, ослаблять ожидаемый результат или объявлять неподтверждённую проверку успешной. Исправления UI принадлежат frontend, сервера и хранилища — backend. Изменение контракта оформляет frontend после обсуждения с backend и QA.

Готовый результат вашей работы:

- согласованный синтетический корпус с независимыми ожидаемыми результатами;
- заполненная матрица `07_ACCEPTANCE_MATRIX.md` для конкретной версии контракта и сборки;
- протоколы отдельно для моков, API и сквозного запуска;
- реестр дефектов с повторяемыми шагами;
- решение о приёмке с перечислением ограничений и непроверенного.

Сначала прочитайте `00_START_HERE.md`, `01_PROJECT_TZ.md`, `02_API_CONTRACT.md`, этот документ, `06_EXECUTION_PLAN.md` и `07_ACCEPTANCE_MATRIX.md`. Предыдущие чаты, архивные планы и знание внутренней инфраструктуры для этой задачи не требуются. Если документы расходятся, зарегистрируйте противоречие; не выбирайте более удобную версию молча.

## 2. Границы демо

Проверяются локальный вход и выход, поиск по метаданным, каскад маркеров, словарь правил компаний, очередь и ручная сортировка, разбор исключений, карантин, восстановление после неоднозначного сбоя и аудит.

Все компании, акторы, пути отображения, имена и содержимое тестовых файлов создаются синтетически. Нельзя брать реальные файлы, обезличенные копии, производные от реальных данных примеры, реальные учётные записи и настройки внутренних хранилищ. Файловые испытания выполняются только в выделенной одноразовой песочнице backend. Браузер получает логические идентификаторы, отображаемые значения и канонические относительные пути, но не физические пути сервера, учётные данные хранилища или команды файловой системы.

В демо нет замены существующего файла, резервирования назначения, удаления файла, автоматического подбора имени при коллизии и отмены файлового перемещения. Переименование по правилу разрешено: фиксированная новая основа плюс исходный последний суффикс расширения. Возврат из карантина — отдельная разрешённая операция с проверкой безопасности, а не универсальная отмена. Откат словаря разрешён: восстановление черновика → актуальный тест → публикация новой версии; уже перемещённые файлы не возвращаются.

Важно различать размещение и состояние. `NO_SCENARIO`/`RULE_CONFLICT` после запуска означают реальную передачу в плоскую папку ручного разбора с исходным именем; успешный исход — `MANUAL_REVIEW`. Занятая штатная цель или занятое имя в ручном разборе оставляют файл во входящих в `REQUIRES_DECISION`. Подтверждённый технический перенос даёт `QUARANTINED`, неоднозначность — `RECOVERY_REQUIRED`. Возврат из карантина даёт `WAITING_READY`, не сразу `READY`. Отдельного интерфейса работы с уже переданными в ручной разбор файлами нет.

Не переносите в приёмку этого пакета архивные D0/I0/T0-переходы, внешние аттестации, допуски к внутренним данным или процедуры выкладки. Приёмка демо сама по себе не разрешает производственное использование. Если фактический рабочий репозиторий отдельно запрещает запуск кода, такой запрет нужно разрешить с владельцем репозитория; этот текст его не отменяет.

## 3. Что именно означает успешная проверка

| Уровень | Что проверяется | Что такой результат не доказывает |
|---|---|---|
| Схема / статическая проверка | Запросы, ответы, перечисления и примеры соответствуют зафиксированному контракту; ссылки и обязательные поля корректны. | Что сервер существует, правила работают или файлы перемещаются безопасно. |
| Mock / UI | Интерфейс проходит сценарий на заранее заданных ответах мок-сервера, включая ошибки и задержки. | Что backend возвращает эти ответы и обеспечивает сохранность файлов. |
| Реальный API / домен | Реализованный backend независимо проверен через API и серверные тесты на синтетической песочнице. | Что пользователь может выполнить сценарий через настоящий интерфейс. |
| E2E | Настоящий frontend обращается к настоящему backend; результат подтверждается UI, API, аудитом и, где нужно, состоянием песочницы. | Готовность внутренних интеграций, доступность в другой среде или допуск к реальным данным. |

Для каждой проверки сохраняйте статус: `NOT_RUN`, `PASS`, `FAIL` или `BLOCKED`. `BLOCKED` означает, что отсутствует необходимая среда, реализация или входное решение; причина и владелец снятия блокировки обязательны. Проверка, которую пытались выполнить и которая дала неверный результат, — `FAIL`, а не `BLOCKED`. Исключение из объёма требует явного решения пользователя и изменения базовой матрицы; пустая строка не считается исключением.

`PASS` допустим только после реального выполнения на указанном уровне. Запланированный тест, созданный тестовый файл, успешная сборка, валидная схема и красивый снимок интерфейса не заменяют выполнения сценария. Нельзя копировать PASS из mock-прогона в колонку E2E. Отсутствие сообщения об ошибке не является доказательством сохранности источника и назначения.

## 4. Синтетический корпус и независимые ожидаемые результаты

До реализации подготовьте описание корпуса и ожидаемые результаты вместе с frontend и backend. QA владеет ожидаемыми результатами, frontend согласует формы API и видимые состояния, backend подтверждает возможность воспроизведения. Примеры в матрице иллюстративны; конкретные ID и полный набор значений фиксируются в корпусе до первого прогона.

В корпусе должны быть:

- минимум два логических корня с непересекающимися наборами файлов;
- иерархия маркеров разной допустимой глубины и несколько сырых написаний: они остаются отдельными значениями, включая различия регистра; неизвестные и неверно расположенные маркеры;
- отдельные файлы для AND, точной фразы, префикса слова, совпадения только в содержимом и совпадения только в старом пути;
- больше подходящих элементов, чем лимит отображаемой выдачи;
- минимум два справочника одной компании: CompanyRuleSet — совокупность активных опубликованных версий всех её справочников. В каждом — типизированные правила `BASENAME`/`RELATIVE_PATH`, маски `*`/`?`, приоритеты, существующие целевые каталоги и фиксированная новая основа имени. Это не словарь поисковых маркеров и не новый DSL;
- безопасное назначение, заранее занятое назначение и два либо более элемента, которые планируют один и тот же ещё свободный путь;
- случаи отсутствующего сценария, равноприоритетного конфликта, известного технического отказа и неоднозначного исхода;
- минимум два синтетических актора для конфликтов редактирования и конкурентных запусков.

Для каждого файла фиксируются стабильный логический ID, исходный относительный путь, значения маркеров, сырые варианты, ожидаемая принадлежность выдачам и ожидаемый исход сортировки. Для каждого поиска фиксируются точные ID результатов в установленном порядке, полное число совпадений и ожидаемые фасеты. Исключение начального состояния: только выбранный корень без текста/цепочки даёт `IDLE`, пустые `items`, `total=null` и первый facet, а не массовую выдачу. Для операций — ожидаемые пути, состояния, код причины и события аудита.

Ожидаемые значения нельзя получать вызовом той же функции сортировки или поиска, которую тестируют. Простые эталонные случаи проверяются по таблице вручную; тесты сравнивают ответ с этим независимым эталоном. Сравнение сервера с его же прогнозом не обнаружит общую ошибку в правиле.

Для проверки отсутствия поиска по содержимому допустимы только заново созданные синтетические файлы. Их содержимое не передаётся в браузер. Для проверки `move_no_replace` backend предоставляет безопасные сведения о контрольных суммах и существовании объектов по логическим ID; реальные пути песочницы не попадают в пользовательские скриншоты, API и экспортируемые отчёты. В корпус включаются `.env`, `README`, `name.`, `archive.tar.gz`, расширение с исходным регистром и файл нулевого размера: правило суффикса и отсутствие фильтрации по типу проверяются явно.

Артефакты размещаются в согласованных каталогах: `fixtures/synthetic` — корпус/эталоны, `contracts/examples` — примеры API, `tests/contract` — независимые контрактные проверки, `tests/e2e` — сквозные проверки, `docs/team` — протоколы и дефекты. Разработчики держат собственные тесты в `frontend/tests` и `backend/tests`. QA не создаёт альтернативную структуру приложения.

## 5. Воспроизводимая среда и протокол запуска

Перед каждым прогоном запишите:

1. Дату и время, проверяющего, ОС/браузер и фактические версии среды выполнения.
2. Commit либо идентификаторы сборок frontend/backend, версию API-контракта, режим `mock` или `real`, конфигурацию лимита выдачи и срока жизни preview.
3. Версию/seed корпуса, его контрольную сумму, ID поколения индекса, полный RuleSet компании и синтетического актора.
4. Фактически использованные команды подготовки, запуска, сброса и тестов из актуального README реализации.
5. Исходное состояние очереди и песочницы; способ включения контролируемых отказов для соответствующих тестов.

В этом пакете не предполагается существование конкретного test runner, сервера или команд. Не запускайте выдуманные инструкции и не пишите, что они сработали. Когда разработчик передаст реализацию, попросите добавить проверенные команды в её README, выполните их и сохраните реальные результаты. Команды должны явно указывать безопасную тестовую среду; для сброса нельзя использовать широкое удаление домашнего каталога или рабочего репозитория.

Обычный прогон:

1. Подготовить свежую синтетическую песочницу штатной командой реализации; проверить seed и исходный инвентарь.
2. Запустить нужный уровень: mock либо реальные frontend/backend. Убедиться, что режим видим и указан в отчёте.
3. Выполнить сценарий с указанными предусловиями. Не использовать остатки другого сценария, кроме явно обозначенных цепочек.
4. Сохранить фактические запросы/ответы, снимки UI и события аудита; удалить из экспортируемых материалов токены сессии и физические пути.
5. Сопоставить результат с независимым эталоном. Для файловых операций отдельно проверить источник, назначение и сохранность ранее существовавшего файла.
6. Записать статус и дефект при расхождении. После исправления повторить исходный случай и соседние регрессионные случаи.

Истечение preview и сбои удобнее воспроизводить контролируемыми часами и точками отказа тестового backend. Такие механизмы должны быть доступны только в тестовом режиме, а не как незащищённые возможности обычного API. Если воспроизведения нет, соответствующая проверка остаётся `BLOCKED`; случайную сетевую ошибку нельзя выдавать за испытание нужной точки сбоя.

## 6. Пакеты работы QA

### QA-01 — базовая приёмка и корпус

Вход: общий ТЗ и проект контракта от frontend. Проверить полноту пользовательских действий и ошибок, согласовать терминологию состояний, эталонный корпус и все строки матрицы. Для поля или правила без определённой семантики создать вопрос владельцу контракта.

Выход: версия матрицы и корпуса, список снятых/открытых вопросов, проверяемые критерии фиксации разделов контракта A — вход/конфигурация/поиск, B — справочники/цели/сортировка, C — партии/карантин/аудит. Backend начинает согласованный раздел, пока frontend готовит следующий и реализует UI на моках. Backend на этапе согласования не обязан уже работать. QA согласует ожидания, но не присваивает результатам реализации PASS.

### QA-02 — проверка моков и интерфейса

Вход: зафиксированный контракт, mock-сервер, UI и команды frontend. Выполнить доступные сценарии входа, каскада, поиска, словаря, выбора файлов и отображения исходов. Проверить загрузку, пустое состояние, ошибку, просроченный preview, повторное нажатие, клавиатуру и сохранение понятного контекста действия.

Выход: отдельный mock/UI-протокол и дефекты frontend. Сценарии физической сохранности файлов и реальной конкуренции пока остаются `NOT_RUN` либо `BLOCKED`, даже если соответствующий ответ нарисован моками.

### QA-03 — независимые API и доменные проверки

Вход: настоящий backend и одноразовая синтетическая песочница. Проверить контракт запросов/ответов, авторизацию, точную семантику поиска и словаря, версии и оптимистическую конкуренцию, snapshot, preflight, состояния файлов, аудит и ошибки.

Выход: API-протокол, результаты независимых сравнений с эталоном, дефекты backend и запросы изменения контракта frontend. Серверные unit-тесты — полезное дополнительное доказательство, но не заменяют независимый API-прогон.

### QA-04 — интеграция, гонки и восстановление

Вход: UI подключён к реальному API, реализованы тестовые точки отказа и наблюдение за песочницей. Пройти пользовательские цепочки и гонки: одновременные claims, повтор одного запроса, занятое после предварительной проверки назначение, устаревший preview, два одинаковых планируемых назначения, потеря ответа и перезапуск процесса.

Выход: E2E-протокол и подтверждения файловой безопасности. Нельзя выводить отсутствие гонок из последовательного запуска двух запросов: нужна управляемая синхронизация или серверный тест с доказуемым пересечением операций.

### QA-05 — решение о выпуске и передача

Вход: исправленные дефекты и зафиксированная кандидатная сборка. Повторить регрессионный набор, проверить запуск со свежего состояния по README, заполнить все статусы и оценить ограничения.

Выход: решение «принято», «не принято» либо «принято с явно согласованными ограничениями», точные версии, ссылки на доказательства и открытые дефекты. Непроверенная безопасность файлов, обход авторизации, подмена акторов, потеря данных или несоблюдение `move_no_replace` не могут быть приняты как косметическое ограничение.

## 7. Ориентир по времени

План — пять относительных недель от согласованного старта, а не календарное обещание. Нагрузка frontend и backend: по 30–35 часов в неделю на каждого. Нагрузка пользователя/QA: 15–20 часов в неделю, всего 75–100 часов за пять недель.

| Неделя | Основной вклад QA | Условие для следующего этапа |
|---|---|---|
| 1 | QA-01: ожидания, корпус, проверка полноты контракта; первые макеты и состояния. | Согласованы правила и измеримые ожидаемые результаты; frontend зафиксировал контракт после обзора backend. |
| 2 | QA-02: mock/UI; ранние проверки доступного API из QA-03. | Основные действия воспроизводятся на моках, расхождения зарегистрированы. |
| 3 | QA-03: реальный API, поиск, словарь, очередь и файловая безопасность. | Backend предоставляет проверяемые ответы и тестовую песочницу; не только заглушки. |
| 4 | QA-04: E2E, конкурентные действия, просрочки и восстановление. | Критические цепочки проходят на реальном соединении; доступны доказательства гонок и сбоев. |
| 5 | QA-05: исправления, регрессия, чистый запуск и передача. | Матрица заполнена доказательствами, ограничения перечислены, решение принято человеком. |

Проверки и исправления идут непрерывно; таблица не требует ждать конца недели для передачи дефекта. При задержке контракта или безопасной песочницы обновляется фактический план, а не сокращается проверка безопасности.

```text
Частота: всегда | иногда; число воспроизведений:
Влияние на пользователя и данные:
Владелец: frontend | backend | контракт (frontend с backend/QA)
Статус; исправляющий commit; результат повторной проверки:
```

Классификация по влиянию: критический — потеря/перезапись данных, выход за песочницу, обход авторизации или неверная атрибуция; высокий — основной сценарий недоступен либо даёт неверный результат; обычный — локальный дефект с понятным обходом; низкий — оформление без влияния на смысл и безопасность. При сомнении описывайте фактическое влияние, не спорьте только о ярлыке.

Ошибка должна сохранять точный код из контракта и связь с журналом. `error.operation_id` обязателен: null, если операция не создана, либо ID зарегистрированной операции при неоднозначном возврате/восстановлении. Событие возврата связывает `operation_id` с `return_operation_id`, а `source_attempt_id` — с исходной попыткой. Не заменяйте разные причины одной записью «что-то пошло не так». При этом пользовательский API/экран не должен выдавать секреты, трассировки стека или физические пути.

При потере ответа проверяйте разные политики повторения: batch/publish/return повторяются с прежним Idempotency-Key и телом; для остальных записей автоматического retry нет. После создания справочника сначала перечитывается список по уникальному имени; после save/restore — объект и ревизия, с сохранением локального ввода. Новый simulation/selection/preview создаётся явным действием. Фиктивный Idempotency-Key на неподдерживающей его операции не является защитой.
