# План работы: фронтенд первым, три участника

Дата: 09.09.2026. Основание: `01_PROJECT_TZ.md`, `02_API_CONTRACT.md`. Это план результатов и зависимостей для команды; он не утверждает наличие готового приложения, установленных зависимостей или работающих тестовых команд.

## 1. Порядок старта

Фронтенд первым описывает пользовательские действия и API. Первый его результат — согласованный контракт входа/поиска с примерами. После него UI и сервер развиваются параллельно. Контракт сортировки фиксируется следующим срезом; ждать окончания поискового UI не нужно.

```text
Frontend: контракт A ──→ клиент + имитация ──→ поиск UI ──→ интеграция поиска
                    │                                              │
Backend:  проверка ──┴─→ вход / индекс / настоящий поиск ────────────┘

Frontend: контракт B/C → справочники / очередь UI → интеграция сортировки
                     │                                      │
Backend:  проверка ───┴─→ правила / очередь / executor ───────┘

QA: эталоны → проверка контрактов → имитация/UI → API → сквозная приёмка
```

Контракт A: вход, сессия, конфигурация, корни, поиск. B: компании, цели, справочники, simulation, выбор и preview. C: партии, фактические исходы, карантин, журнал. Семантика всех трёх уже описана в пакете; Frontend превращает её в проверяемый OpenAPI и примеры.

## 2. Стартовая подготовка без потери контекста

- [ ] Инициатор передаёт каждому весь пакет; участники получают доступ к одному общему закрытому Git-репозиторию.
- [ ] Команда синхронизирует владельца API, план и ссылки в `AGENTS.md`, README и прежних handoff. Старый укороченный контракт не остаётся параллельным нормативом.
- [ ] Backend и Frontend фиксируют точные рабочие версии инструментов и команду чистой сборки; QA записывает тестовую среду.
- [ ] Условия внешней работы проверяются на текущем репозитории: только вымышленные данные, локальная генерируемая песочница, отсутствие реального подключения к хранилищу.
- [ ] Если прежняя проверка целостности жёстко требует старые routes/status strings, её обновляют и отдельно проверяют назначение каждого ограничения. Изменение manifest само по себе не является доказательством готовности продукта.
- [ ] В статусе проекта раздельно записывают: документы подготовлены, контракт согласован, mock проверен, API проверен, интеграция принята. Нельзя автоматически перевести все статусы в PASS.

Эта подготовка выполняется в одном согласованном изменении рабочего репозитория. Пользовательские решения о новых ролях уже заданы; повторно опрашивать инициатора о том, кому принадлежит API, не нужно. Неизвестные параметры внутреннего хранилища не мешают проектировать интерфейс на синтетике.

## 3. Единая карта репозитория

```text
frontend/
  src/features/{auth,search,dictionaries,sorting,quarantine,audit}/
  src/api/generated/          клиент и типы из OpenAPI
  src/mocks/                  имитация API с общими сценариями
  tests/                      компонентные и браузерные тесты frontend
backend/
  app/{api,domain,services,ports,adapters}/
  migrations/
  tests/{unit,contract,integration}/
contracts/
  openapi/memoza-demo-v1.yaml  владелец Frontend
  examples/                   валидные запросы, ответы, ошибки
fixtures/synthetic/           общий вымышленный корпус и эталоны
tests/contract/               проверки публичной границы
tests/e2e/                    общие сквозные сценарии
infra/                        сборка и запуск, без реальных секретов
docs/team/                    этот пакет, статусы, журнал решений
```

Это целевая структура; её наличие в существующем репозитории не предполагается. Backend владеет серверными миграциями и `infra/`, Frontend — браузерной сборкой. QA вправе менять тесты/эталоны, но исправление продукта назначается соответствующему разработчику.

## 4. Сроки и доступность

Плановая длительность — **5 рабочих недель от фактического старта**, плюс 1–2 недели резерва на дефекты и воспроизводимость. Это оценка для Frontend и Backend по 30–35 продуктивных часов в неделю, QA по 15–20. Codex помогает писать и проверять код; время совместных решений, запуска стенда и реальной проверки входит в эту загрузку.

Первая демонстрация поиска на имитации API — ориентир конец первой недели. Сквозной поиск с настоящим сервером — конец второй. Сквозная сортировка — конец четвёртой. Итоговая приёмка обеих функций — пятая неделя. Это контрольные точки с критериями, не утверждение о готовности на календарную дату.

Если работа идёт только вечерами по 10–15 часов в неделю, рассчитывать на те же пять календарных недель нельзя. Календарь пересчитывается по доступности наиболее загруженной роли; ориентир для такой загрузки — порядка 10–15 недель, с уточнением после первой недели фактической скорости.

| Период | Frontend | Backend | QA | Проверяемый результат |
|---|---|---|---|---|
| День 1 | FE-01: экраны и контракт A | Проверка A, модель данных, окружение BE-01 | QA-01: основные эталоны | Согласованы auth и поисковый запрос/ответ |
| Дни 2–3 | FE-02: B/C, generated client, mocks | BE-01, ранняя проверка no-replace в sandbox; начало BE-02 | Схемы ошибок, эталоны поиска/правил | Контракты всех экранов и отрицательных исходов |
| Дни 4–5 | FE-03: вход и поиск на mocks | BE-02: metadata/parser/index; BE-04a: чтение incoming/readiness | QA-02: навигация, точные counts, пустые/ошибочные состояния | Первая mock-демонстрация, session API работает |
| Неделя 2 | FE-03/05: реальный поиск; начало FE-04 | BE-02 завершение; BE-03 matcher/версии | QA-03: поиск API, независимые эталоны | Поиск принят на настоящем API |
| Неделя 3 | FE-04: справочники, preview, очередь | BE-04a готов; BE-03 simulation/publish; BE-04b snapshots/preview; начало BE-05 | Проверка правил, версий, снимков и stale cases | Справочник тестируется/публикуется, preview реален |
| Неделя 4 | FE-05: партии, карантин, журнал; FE-06 при готовом UI | BE-05: перемещения, конкуренция, восстановление | QA-04: файлы/журнал/races, сравнение с mock | Обе функции сквозные, основные ошибки проверены |
| Неделя 5 | Исправления UI/контракта, согласованная помощь backend | BE-06: сборка, миграции, restart, исправления | QA-05: чистый запуск, приёмка, дефекты, передача | Воспроизводимая демоверсия и отчёт |

BE-04 разбивается по результатам, чтобы не создать цикл зависимостей: **BE-04a** обнаружение/готовность/чтение очереди зависит только от BE-01; **BE-04b** selection/preview зависит от BE-03 и BE-04a. Simulation BE-03 потребляет READY-набор BE-04a. Ранний тест атомарного no-replace не ждёт четвёртой недели.

## 6. Как сдавать работу ежедневно

Каждый день короткая запись в общем статусе: завершённый результат, ссылка на commit/запрос слияния, выполненные проверки, препятствие и следующий результат. Codex может подготовить запись, человек проверяет её достоверность.

Каждый запрос слияния содержит:

- ID задачи и требования, которые закрывает изменение.
- Что теперь умеет пользователь или API.
- Версию контракта и изменения схем/миграций, если есть.
- Реальные команды проверок, результаты и режим: MOCK / REAL_API / E2E.
- Известные ограничения и способ воспроизвести результат.

Ветки короткие: `codex/frontend-<task>`, `codex/backend-<task>`, `codex/qa-<task>`. Работать в одной репозитории не значит править одну общую рабочую папку одновременно: у каждого свой checkout/ветка. Слияния небольшие и частые; общий контракт проходит проверку обоих разработчиков и QA. Конкретный способ push/review соответствует принятой конфигурации репозитория; этот документ сам её не меняет.

## 7. Проверки, которые команда должна реализовать

| Проверка | Владелец | Что доказывает |
|---|---|---|
| Валидация OpenAPI и всех examples | Frontend | Структура контракта внутренне согласована |
| Генерация клиента и отсутствие diff после повторной генерации | Frontend | Клиент соответствует версии схемы |
| UI/component/browser с mocks | Frontend | Поведение интерфейса при известных ответах |
| Серверные unit/contract/integration | Backend | Алгоритмы, сериализация, БД, индекс, sandbox |
| Независимые exact golden checks | QA | Реализация соответствует ожидаемому бизнес-результату |
| E2E через UI и настоящий сервер | Frontend + QA, Backend исправляет сервер | Обе части действительно взаимодействуют |
| Проверка после restart и сетевого retry | Backend + QA | Нет повторных файловых действий и потери истории |
| Чистый запуск на отдельной копии | QA | Другой человек может воспроизвести поставку |

Имена команд тестов фиксируются в README после выбора инструментов и появления runner. Не копировать в отчёт вымышленные `npm test`/`pytest` команды как уже выполненные. Старые context tests полезны для своего назначения, но не заменяют эти проверки.

## 8. Завершение

Результат передаётся как версия репозитория с инструкцией запуска, зафиксированным контрактом, примерами, синтетическими данными, тестами и отчётом QA. Критические дефекты и основные функциональные несоответствия закрыты независимым повторным тестом. Незначительные известные недочёты перечислены с влиянием и сроком.

Реальные данные и параметры инфраструктуры согласуются для следующего внутреннего этапа. Успешная внешняя демонстрация подтверждает пользовательскую и программную логику на синтетике; испытания фактического хранилища и промышленного масштаба оформляются отдельно.
